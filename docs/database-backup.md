# Резервное копирование и восстановление PostgreSQL

**Автор:** Васильев Юрий, 4П1.23

## 1. Объём

Скрипт [database-backup.ps1](../scripts/database-backup.ps1) создаёт логическую копию базы сервиса postgres выбранного проекта Compose и восстанавливает её в новую базу того же PostgreSQL. Он не меняет подключение основного приложения, не удаляет базы и не перезаписывает существующие архивы.

Архив pg_dump в формате custom содержит схему, данные, индексы, ограничения, состояния последовательностей и flyway_schema_history. Роли кластера, пароли и конфигурация PostgreSQL в эту копию одной базы не входят. При восстановлении владельцем объектов становится пользователь выбранного Compose, исходные права доступа не переносятся: используются --no-owner и --no-privileges.

Применяются pg_dump/pg_restore из контейнера PostgreSQL 18.6. Локальная установка PostgreSQL и JDK не требуется. Нужны PowerShell 7, Docker CLI в PATH, заполненное окружение Compose и работающий postgres. [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html) формирует согласованный снимок работающей базы; для сравнения снимков до и после проверки не следует параллельно менять контрольные данные.

## 2. Создание копии

Запустить окружение по [инструкции Compose](container-runtime.md). Контрольные заявки можно подготовить [коллекцией BL-20](api-demo.md) на пустой базе. Из корня проекта:

```powershell
docker compose up -d --wait --wait-timeout 180
.\scripts\database-backup.ps1 -Action Backup -FilePath .\backups\support-demo.dump
Get-FileHash .\backups\support-demo.dump -Algorithm SHA256
```

Скрипт создаёт каталог назначения, вызывает pg_dump --format=custom --file во временный файл внутри контейнера, проверяет его оглавление через pg_restore --list и копирует на компьютер через [docker cp](https://docs.docker.com/reference/cli/docker/container/cp/). Бинарный архив не проходит через текстовый конвейер PowerShell. После успешного копирования временный локальный файл переименовывается в выбранный путь без перезаписи существующего файла.

Результат содержит action, имя базы, абсолютный путь, размер и SHA-256. Сохранить хеш вместе с результатами проверки. Для следующей копии выбрать другое имя; наличие файла не считается разрешением его заменить. Каталог backups исключён из Git и контекста Docker, а gradlew clean его не удаляет. Копию для долговременного хранения нужно отдельно перенести на выбранный носитель: наличие файла рядом с проектом не защищает от потери самого компьютера.

Для другого проекта или отдельного файла окружения:

```powershell
.\scripts\database-backup.ps1 -Action Backup `
  -FilePath .\backups\support-lab.dump `
  -EnvFile .\.env.lab -ProjectName support-lab
```

Те же EnvFile и ProjectName должны использоваться при запуске этого Compose. Без параметров используется корневой compose.yaml и его обычное окружение. Скрипт читает POSTGRES_DB и POSTGRES_USER из работающего контейнера, пароль в вывод не попадает. Файл окружения сам по себе не запускает контейнеры.

## 3. Восстановление в отдельную базу

Выбрать новое имя, например support_restore_check:

```powershell
.\scripts\database-backup.ps1 -Action Restore `
  -FilePath .\backups\support-demo.dump `
  -TargetDatabase support_restore_check
```

Имя содержит от 1 до 63 строчных латинских букв, цифр и подчёркиваний и начинается с буквы. Исходное имя POSTGRES_DB и любая уже существующая база запрещены. Сначала проверяются параметры и отсутствие целевой базы, затем архив копируется в контейнер и проверяется pg_restore --list. После этого createdb создаёт базу из template0, а pg_restore --single-transaction --exit-on-error восстанавливает архив целиком.

[Одна транзакция pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html) откатывает восстановленные объекты при ошибке. Создание базы выполняется раньше и отдельно: при сбое восстановления новая база может остаться пустой. Скрипт не удаляет её автоматически. Оглавление не доказывает целостность всех данных архива, поэтому успешный pg_restore и последующая проверка обязательны. Для повторной попытки использовать новое имя, а состояние неудачной базы разбирать отдельно.

Временный архив контейнера и незавершённый локальный файл очищаются в finally. Успешный исходный архив сохраняется. Если контейнер недоступен во время очистки, выводится предупреждение с указанием необходимости удалить временный файл внутри него. Нет команд dropdb, DROP DATABASE, pg_restore --clean или --create.

## 4. Проверка восстановленной базы

Сначала сравнить записи categories, tickets, ticket_status_history и flyway_schema_history, столбцы, ограничения, индексы и состояния sequences categories_id_seq и ticket_status_history_id_seq. Для небольшого учебного набора можно сохранить отсортированные JSON-снимки через psql. Пример для заявок:

```powershell
docker compose exec -T postgres psql -U support_service -d support_service `
  -At -v ON_ERROR_STOP=1 -c 'SELECT jsonb_agg(t ORDER BY id) FROM tickets t'
docker compose exec -T postgres psql -U support_service -d support_restore_check `
  -At -v ON_ERROR_STOP=1 -c 'SELECT jsonb_agg(t ORDER BY id) FROM tickets t'
```

Если DB_USERNAME или DB_NAME изменены, заменить их в командах. Для категорий и истории сортировать по id, для миграций по installed_rank. Совпадение количества строк не заменяет сравнение всех значений, включая UUID, русские строки и временные метки. Представление pg_get_constraintdef/pg_indexes может отличаться после повторного разбора SQL: в проверке BL-22 отдельно рассмотрены эквивалентные приведения типов массивов, исходные определения сохранены в артефактах.

Для проверки API запустить отдельный экземпляр приложения на восстановленной базе. Порт 8081 должен быть свободен, основной app продолжает работать с исходной базой:

```powershell
docker compose run -d --no-deps --name support-restore-check `
  -p 127.0.0.1:8081:8080 `
  -e DB_URL=jdbc:postgresql://postgres:5432/support_restore_check app
Invoke-RestMethod 'http://localhost:8081/actuator/health/readiness'
```

Дождаться status UP, повторяя запрос при необходимости. Flyway должен подтвердить уже восстановленные версии 1 и 2, а Hibernate проверить схему. Сравнить категории, список, каждую заявку и её историю, а также отчёт с исходным API. JSON-объекты сравниваются по значениям, без требования одинакового порядка ключей; порядок элементов массивов сохраняется.

Затем только в восстановленной базе создать новую категорию без явного id, создать заявку через API и выполнить допустимые переходы. Новые ID категории и истории должны продолжить сохранённые sequences и не пересекаться с существующими. Проверить, что исходные таблицы и sequences не изменились. После проверки остановить отдельный экземпляр:

```powershell
docker stop support-restore-check
docker rm support-restore-check
```

Эти команды относятся только к созданному проверочному контейнеру. Базы и том остаются сохранены. Основной Compose останавливается через down без -v, как описано на BL-21. Восстановление в том же кластере проверяет логическую копию; запуск на другом сервере и аварийное переключение в этом этапе не выполнялись.

Значения enum, условия, имена и остальная структура не изменились. Сравнение нормализовало только эту конкретную форму; прочие различия не игнорировались. Определения до и после сохранены в build/bl22-schema-comparison.json.

Исходный архив не изменился при отрицательных проверках. Неудачная база support_restore_bl22_867530fd_broken осталась без восстановленных объектов, как предусмотрено скриптом. Это контролируемое повреждение копии для проверки отката, а не дефект приложения. Подтверждены OPS-03, AC-11.1, AC-11.2 и NFR-07. Сохранность при пересоздании контейнеров уже подтверждена на BL-21; она не подменяет выполненное здесь восстановление из архива.

Свидетельства: build/bl22-backup-result.json, build/bl22-restore-result.json, build/bl22-source-before.json, build/bl22-source-after.json, build/bl22-restored-before.json, build/bl22-restored-after.json, build/bl22-snapshot.sql, build/bl22-http-responses.json, build/bl22-api-verification.json, build/bl22-guard-verification.json, build/bl22-truncated-error.log и build/bl22-restore-app.log. build игнорируется Git и удаляется clean; архив в backups хранится отдельно от build.

После проверки оба экземпляра приложения и PostgreSQL остановлены. Том support-bl21-dc5ac8f2_postgres-data с исходной и тестовыми базами сохранён, архив остаётся в backups. Временные архивы внутри контейнера удалены; проверка зафиксирована в build/bl22-cleanup.json.

Бизнес-код и JUnit-тесты не менялись. Полный набор из 507 выполнений подтверждён на BL-20 и на BL-22 повторно не запускался. Здесь выполнены реальные операции pg_dump/pg_restore, сравнение БД и API, запись новых данных и пять отрицательных проверок скрипта. Диагностика отказов и AC-11.3/AC-11.4 остаются BL-23; публикация и доставка остаются последующими этапами.
