## 1. Проблема и цель

В организации обращения в техническую поддержку поступают через разные каналы. Из-за отсутствия единого учёта сотрудники теряют заявки, не отслеживают сроки и вручную подготавливают отчёты.

Цель проекта - разработать серверное приложение для централизованного учёта заявок, контроля допустимых изменений их состояния и получения статистики. В рамках практики необходимо пройти полный цикл: анализ, проектирование, реализация, тестирование, контейнеризация и автоматическое развёртывание.

Результат предоставляется в виде REST API. Работа с ним демонстрируется через Swagger UI и подготовленную коллекцию HTTP-запросов.

## 2. Пользователи и заинтересованные стороны

| Участник | Потребность |
|---|---|
| Сотрудник, регистрирующий обращение | Создать заявку и просмотреть её текущее состояние |
| Специалист технической поддержки | Найти заявку, уточнить данные, установить приоритет и срок, изменить статус |
| Руководитель технической поддержки | Получить статистику за период и оценить количество открытых просроченных заявок |
| Ответственный за эксплуатацию | Запустить приложение, проверить его состояние, сохранить и восстановить данные, выполнить откат |
| Преподаватель | Проверить выполнение требований, историю разработки, тесты и развёртывание через pipeline |

Эти роли описывают потребности пользователей. Разграничение доступа и аутентификация в обязательном объёме задания не установлены.

## 3. Границы проекта

### Входит в объём

- Один серверный сервис на Java и Kotlin/JVM с базой данных PostgreSQL.
- Регистрация и просмотр заявок, редактирование разрешённых полей.
- Справочник категорий, приоритеты, сроки и управление статусами.
- История изменения статусов и транзакционное сохранение изменений.
- Список заявок с фильтрацией и пагинацией.
- Статистика через `GET /api/reports/summary`.
- Валидация, единый формат ошибок и описание API.
- Миграции, демонстрационные данные и автоматизированные тесты.
- Docker Compose, резервное копирование, восстановление и диагностика.
- CI/CD с публикацией образа, запуском на учебном стенде, проверкой и демонстрацией отката.
- Спецификация, диаграммы, backlog, тест-план, отчёты и материалы защиты.

### Не входит в обязательный объём

- Отдельный графический интерфейс, мобильное приложение.
- Микросервисная архитектура и Kubernetes.
- Интеграция с почтой, мессенджерами и внешними системами приёма обращений.
- Авторизация, управление учётными записями, уведомления и вложения.
- Удаление заявок и повторное открытие завершённых или отменённых заявок.

Контекст о разных каналах обращений описывает исходную проблему, но не устанавливает требование интегрировать эти каналы в приложение.

## 5. Бизнес-правила

| ID | Правило |
|---|---|
| BR-01 | Заголовок и категория обязательны |
| BR-02 | Допустимые приоритеты: `LOW`, `MEDIUM`, `HIGH` |
| BR-03 | Начальный статус заявки - `NEW` |
| BR-04 | Основная последовательность переходов: `NEW` → `IN_PROGRESS` → `RESOLVED` |
| BR-05 | Отмена разрешена только из `NEW` и `IN_PROGRESS` |
| BR-06 | Завершённые и отменённые заявки нельзя редактировать или повторно открывать |
| BR-07 | Изменение статуса и добавление записи истории выполняются атомарно: обе операции сохраняются вместе либо обе отменяются |
| BR-08 | Заявка просрочена, если её срок истёк, а текущий статус - `NEW` или `IN_PROGRESS` |
| BR-09 | Отсутствующая заявка возвращает HTTP `404`, ошибка валидации - `400`, запрещённый переход статуса - `409` |
| BR-10 | Запрещённый переход не изменяет ни статус, ни историю заявки |

В задании не определено программное имя статуса отмены. В проекте выбран `CANCELLED`; время закрытия заполняется и при решении, и при отмене. Обязательность полей, значения по умолчанию и ограничения длины зафиксированы в [модели данных](data-model.md), а правила времени и переходов - в [процессе обработки](ticket-workflow.md). Эти уточнения отделены от исходных обязательных правил.

## 6. Статистика и интеграция Kotlin

| ID | Требование |
|---|---|
| KR-01 | Все показатели рассчитываются по одной выборке: заявки, созданные в интервале `[from, to)` |
| KR-02 | Отчёт содержит количество созданных заявок, распределение по текущим статусам и приоритетам, количество открытых просроченных заявок и среднее время решения |
| KR-03 | Среднее время решения рассчитывается только для текущего статуса `RESOLVED` как разница времени закрытия и создания; при отсутствии таких заявок возвращается `null` |
| KR-04 | Модели отчёта используют Kotlin `data class`, nullable-типы и безопасную обработку отсутствующих значений |
| KR-05 | Расчёт статистики использует операции над коллекциями и взаимодействует с Java-компонентами работающего приложения |
| KR-06 | Минимум три теста написаны на Kotlin; хотя бы один проверяет Java-компонент |
| KR-07 | Итоговый отчёт объясняет два решения, на которые повлияли особенности Kotlin |

Наличие только `build.gradle.kts` не выполняет требование о бизнес-функции на Kotlin.

## 8. Требования к проверке качества

- Тест-план связывает требования, пользовательские истории и критерии приёмки с проверками.
- Не менее 10 модульных тестов проверяют переходы статусов, валидацию, просрочку и статистику.
- Не менее 6 интеграционных тестов используют PostgreSQL через Testcontainers и проверяют REST API, миграции, фильтрацию и сохранение истории.
- Не менее 2 сквозных сценариев проверяют полный жизненный цикл заявки и запрещённую операцию без изменения данных.
- Обязательные границы: пустая выборка, отсутствие завершённых заявок, момент наступления срока, неверный период отчёта и неизвестный идентификатор.
- Формируется отчёт о покрытии бизнес-логики Java и Kotlin. Обязательный численный порог покрытия в задании не указан.
- Найденные дефекты описываются с шагами воспроизведения; минимум один исправленный дефект получает регрессионный тест. Дефекты и результаты выполнения фиксируются по фактическим наблюдениям.
- Проверяется сохранность данных после перезапуска и корректность восстановления резервной копии.

## 9. Требования к CI/CD и эксплуатации

Pipeline должен получать исходный код, подготавливать среду, проверять форматирование или выполнять статический анализ Java и Kotlin, собирать приложение, запускать тесты и публиковать отчёты о тестировании и покрытии.

Для pull request выполняются проверки без развёртывания. После успешного слияния в основную ветку pipeline собирает и публикует контейнерный образ с тегом по идентификатору коммита, развёртывает его на учебном стенде и проверяет работоспособность приложения. Ошибки тестирования блокируют публикацию образа и развёртывание.

Учебный стенд предоставляет преподаватель; допускается локальная виртуальная машина с runner. Публикация образа без его запуска и проверки не считается завершённым CD.

Необходимо продемонстрировать возврат к предыдущему образу приложения и описать диагностику трёх ситуаций: база недоступна, приложение не проходит health check, миграция завершается ошибкой.

## 10. Материалы и условия завершения

Для сдачи необходимы:

1. Git-репозиторий с кодом, историей разработки, ветками и pull request.
2. Спецификация, не менее шести пользовательских историй с проверяемыми критериями, диаграмма процесса, ER-диаграмма и backlog с приоритетами и трудозатратами.
3. Миграции и демонстрационные данные.
4. Описание API с примерами и коллекция запросов.
5. Тест-план, автотесты, результаты выполнения, покрытие и описания дефектов.
6. Dockerfile, Compose и конфигурация pipeline.
7. README с запуском, проверкой, резервным копированием, восстановлением и откатом.
8. Краткий отчёт о выполненных задачах, фактических затратах времени, дефектах и ограничениях решения.
9. Ссылка на успешный запуск pipeline и идентификатор развёрнутого образа.

Обязательные условия зачёта независимо от баллов: воспроизводимый запуск, работающая бизнес-функция на Kotlin, успешные автоматизированные тесты и продемонстрированное развёртывание через pipeline.

Защита длится 10-15 минут и включает связь требования с кодом и тестом, создание заявки и изменение статуса, отчёт, взаимодействие Java и Kotlin, отклонение запрещённой операции, pipeline, приложение на стенде, диагностику и откат.
