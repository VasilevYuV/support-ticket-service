# Сквозные сценарии обработки заявки

**Автор:** Васильев Юрий, 4П1.23

## 1. Объём BL-17

Класс ticket.scenario.TicketLifecycleE2ETest реализует E2E-01 и E2E-02 из [тест-плана](test-plan.md). Два метода дают три выполнения: жизненный цикл, запрет изменения RESOLVED и запрет изменения CANCELLED.

Запускается полное приложение Spring Boot на случайном HTTP-порту и PostgreSQL 18.6 через Testcontainers. Все предметные действия выполняются HTTP-запросами: выбор категории, создание, чтение, редактирование, переходы, история, список и отчёт. Сервисы, репозитории и миграции настоящие. Подменяется только Clock в тестовом контексте; публичного маршрута изменения времени нет.

Тесты находятся в модуле ticket, в отдельном пакете scenario. Общий ApiTestSupport очищает заявки и историю перед каждым выполнением, управляет HTTP-клиентом и проверяет ответы по OpenAPI. SQL используется для очистки и независимого чтения снимков, но не для создания промежуточных состояний сценария. Бизнес-код, зависимости и контракт не изменены.

## 2. E2E-01: жизненный цикл и отчёт

Метод completesLifecycleAndCalculatesReport проходит все восемь бизнес-операций API.

| Шаг | Действие | Проверка |
|---|---|---|
| 1 | GET категорий, выбор ID из ответа, POST заявки | Четыре категории, 201 и Location; NEW, MEDIUM, пустое описание, время создания и категория из запроса |
| 2 | GET заявки и истории | Заявка совпадает с ответом создания, история пуста |
| 3 | PUT details и повторное чтение | Описание «Проверено подключение.», HIGH, новый срок; id, title, category и createdAt прежние, история пуста |
| 4 | Clock на +60 секунд, PATCH IN_PROGRESS | Нет closedAt и просрочки; первая история NEW -> IN_PROGRESS с точным changedAt |
| 5 | Clock на +3600 секунд, PATCH RESOLVED | closedAt совпадает с новым временем, редактируемые поля сохранены, идентификатор и время создания прежние |
| 6 | GET заявки, истории, списка и отчёта | Две последовательные истории с возрастающими ID, одна заявка в списке, корректные показатели отчёта |
| 7 | Независимое чтение PostgreSQL | Одна заявка, две истории, точные сохранённые описание, приоритет, created_at, due_at и closed_at |

Время создания: 2035-12-31T23:00:00.123456Z. Начальный срок на 300 секунд позже, после редактирования на 600 секунд позже. Перевод в работу происходит через 60 секунд, завершение через 3600 секунд, уже в 2036 году. В Clock добавляется 789 наносекунд, которые приложение отбрасывает до точности микросекунд.

Период отчёта: [2035-12-31T23:00:00.123456Z, 2035-12-31T23:00:01.123456Z). Создание попадает в период, закрытие находится за его пределами. Ожидаются totalCreated=1, RESOLVED=1, HIGH=1, все остальные группы нулевые, openOverdue=0 и averageResolutionSeconds=3600. Список содержит ту же полную заявку и totalElements=1, totalPages=1.

## 3. E2E-02: запрет без изменения данных

Метод rejectsTerminalChangesWithoutChangingAnyView параметризован двумя состояниями: RESOLVED и CANCELLED. Для каждого варианта через HTTP создаётся отдельная заявка, переводится в IN_PROGRESS через 60 секунд и закрывается через 3600 секунд. До проверки запретов подтверждены терминальный статус, closedAt и две правильные записи истории.

Снимок до операций включает:

- Все строки и поля categories, tickets и ticket_status_history, упорядоченные по id.
- Полный JSON заявки и её истории.
- Полный JSON страницы списка.
- Полный JSON отчёта за период создания.

Попытка возврата в IN_PROGRESS даёт 409 STATE_CONFLICT. После неё заново читаются все данные и ответы, снимок полностью сравнивается с исходным. Затем выполняется PUT с изменением всех трёх редактируемых полей: описания, приоритета и срока. Он также даёт 409, и сравнение повторяется отдельно. Таким образом, проверяется отсутствие изменений после каждого запрета, а не только после пары запросов.

Clock между снимками не меняется. Для RESOLVED ожидается среднее 3600 секунд, для CANCELLED среднее null. В обоих случаях приоритет остаётся MEDIUM, открытая просрочка равна нулю. Проверка ошибки также контролирует timestamp, HTTP/status, код, путь и структуру violations.

## 4. Запуск и разделение наборов

Нужны Java 25 и работающий Docker:

```powershell
.\gradlew.bat e2eTest
```

Задача выбирает только классы *E2ETest в пакетах ru.vasilev.support.*.scenario. integrationTest выбирает controller и database.migration и не включает E2E. unitTest также не выбирает scenario. Обычный test выполняет все уровни, включая E2E; задача e2eTest запускается отдельно и не добавляет второй прогон в build.

Артефакты: build/test-results/e2eTest и build/reports/tests/e2eTest/index.html. Для принудительного повторного исполнения добавляется --rerun-tasks. В исходном классе методы подписаны идентификаторами E2E-01 и E2E-02; в XML два выполнения второго метода различаются параметром terminalStatus. Параметризованные варианты E2E-02 не выдаются за два самостоятельных сценария.

Проверки относятся к полному приложению в тестовом процессе. Запуск собранного образа на стенде, постоянный том и доставка через pipeline проверяются на последующих этапах.

## 5. Результаты BL-17

Проверено 11.11.2026, ветка feature-c/end-to-end-scenarios от 39efe53, до коммита этапа. Окружение: Windows, Java 25, Kotlin 2.4.21, Docker, PostgreSQL 18.6.

Команда: `.\gradlew.bat spotlessApply build e2eTest integrationTest --no-daemon --console=plain`.

| Проверка | Результат |
|---|---|
| E2E-01 | Успешно, 1 выполнение |
| E2E-02 | Успешно для RESOLVED и CANCELLED, 2 выполнения |
| Отдельный e2eTest | 3 выполнения, 0 ошибок, 0 пропусков |
| Полный test | 505 выполнений, 0 ошибок, 0 пропусков |
| Отдельный integrationTest | 371 выполнение, 0 ошибок, 0 пропусков; классов E2E нет |
| Сборка и оформление | Успешно |

Полный набор состоит из 129 модульных и технических проверок, 371 интеграционной, 3 выполнений E2E и 2 проверок каркаса. Повторные запуски задач не увеличивают количество уникальных методов и сценариев. Итоговые XML подтверждают отдельный состав e2eTest и отсутствие scenario-класса в integrationTest.

В первой попытке один тест остановился из-за ошибочного приведения JDBC Timestamp к OffsetDateTime при чтении снимка. Проверка исправлена на Timestamp.toInstant; это ошибка теста, а не дефект приложения. После исправления весь набор успешен. Новых дефектов бизнес-логики на BL-17 не выявлено.

Выполнены E2E-01 и E2E-02. Следующий этап BL-18 проверяет журнал фактически найденных дефектов и регрессионные свидетельства. Измерение покрытия, эксплуатация и доставка остаются отдельными задачами.
