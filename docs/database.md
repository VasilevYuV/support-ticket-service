# PostgreSQL и миграции

**Автор:** Васильев Юрий, 4П1.23

Схема соответствует [модели данных](data-model.md). Она создаётся Flyway при запуске приложения. JPA подключён с `ddl-auto: validate`; начиная с BL-07 Hibernate проверяет сущности категорий и заявок из предметных модулей. Сущность истории пока не добавлена. Структуру таблиц и ограничения дополнительно проверяют SQL-тесты.

## 1. Миграции

Файлы находятся в `src/main/resources/db/migration`:

| Версия | Файл | Содержание |
|---|---|---|
| 1 | `V1__create_support_schema.sql` | Категории, заявки, история, первичные и внешние ключи, CHECK, уникальность и четыре дополнительных индекса |
| 2 | `V2__seed_categories.sql` | Оборудование, Программное обеспечение, Доступы, Сеть |

Flyway ведёт таблицу `flyway_schema_history`, сверяет контрольные суммы и не запускает успешно применённую версию повторно. Уже применённые миграции не редактируются; изменение схемы оформляется новым файлом. Автоматический `clean` отключён. `schema.sql`, `data.sql` и создание таблиц Hibernate не используются.

Миграции не создают демонстрационные заявки. Внешние ключи не разрешают каскадное удаление. CHECK истории допускает четыре пары переходов; связь цепочки истории с текущим состоянием заявки будет обеспечивать сервис в одной транзакции. Ограничения SQL не заменяют валидацию API.

Основание настройки: [инициализация базы в Spring Boot](https://docs.spring.io/spring-boot/how-to/data-initialization.html).

## 2. Настройки подключения

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/support_service` | JDBC-адрес базы |
| `DB_USERNAME` | `support_service` | Пользователь PostgreSQL |
| `DB_PASSWORD` | Пустое значение | Пароль; задаётся перед запуском |
| `SERVER_PORT` | `8080` | HTTP-порт приложения |

Параметры передаются через окружение процесса. Файл `.env` сам по себе не загружается Spring Boot. Пустой пароль не является настройкой доверенного доступа к базе. Для локального примера используется явно указанный учебный пароль; реальные учётные данные в Git не записываются.

`spring.jpa.open-in-view=false` запрещает держать JPA-сессию на время обработки всего HTTP-запроса. Время JDBC настроено на UTC. `/actuator/health` включает состояние подключения к PostgreSQL; группа `/actuator/health/readiness` включает `readinessState` и `db`. Liveness не зависит от базы. Детали подключения в публичном ответе health не раскрываются.

## 3. Локальная база в Docker

Полные команды запуска приведены в [README](../README.md). Для PostgreSQL 18 именованный том монтируется в `/var/lib/postgresql`, согласно [описанию официального образа](https://github.com/docker-library/docs/blob/master/postgres/README.md). Порт базы публикуется только на `127.0.0.1`.

Для проверки схемы после запуска приложения:

```powershell
docker exec support-postgres psql -U support_service -d support_service -c '\dt'
docker exec support-postgres psql -U support_service -d support_service -c 'SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;'
docker exec support-postgres psql -U support_service -d support_service -c 'SELECT id, name FROM categories ORDER BY id;'
```

Ожидаются три предметные таблицы, служебная таблица Flyway, две успешные миграции и четыре категории. При повторном запуске приложения эти записи сохраняются.

Остановка и последующее включение существующего контейнера:

```powershell
docker stop support-postgres
docker start support-postgres
```

Команду `docker run` используют только при первом создании контейнера. Данные остаются в именованном томе; изменение переменных `POSTGRES_*` не меняет уже созданных пользователей и базу. Резервное копирование и восстановление проверяются на отдельном этапе.

## 4. Автоматические проверки

```powershell
.\gradlew.bat test --tests '*DatabaseMigrationTest'
```

Нужен работающий Docker Engine с Linux-контейнерами. `PostgresTestConfiguration` создаёт отдельный PostgreSQL 18.6 через Testcontainers и передаёт подключение Spring Boot через `@ServiceConnection`. Тесты не используют локальную базу из `DB_URL`; имя, порт и учётные данные предоставляет контейнер. Его жизненным циклом управляет Spring, после завершения тестов он удаляется. Основание: [интеграция Testcontainers со Spring Boot](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html).

`DatabaseMigrationTest` проверяет:

- создание таблиц, индексов, категорий и истории Flyway на пустой базе;
- повторный вызов миграций без дубликатов;
- значения по умолчанию, допустимые NULL, микросекунды и границы длины Unicode;
- обязательные поля, неизвестные статусы и приоритеты, отсутствующую категорию;
- все сочетания статуса с отсутствующим, ранним, равным и поздним временем закрытия;
- все 16 пар статусов истории, четыре разрешённых и 12 запрещённых;
- обязательные поля истории, её внешний ключ и запрет удаления связанных записей;
- уникальность и непустое название категории.

Изменяющие данные проверки выполняются в транзакциях с откатом. После ожидаемого нарушения ограничения PostgreSQL транзакция считается прерванной, поэтому каждый параметризованный вариант использует отдельную транзакцию. Повторный запуск Flyway проверяется вне транзакции теста. Это разные варианты проверки схемы, а не отдельные бизнес-сценарии для формального достижения минимального количества тестов.

Отчёты: `build/reports/tests/test/index.html` и `build/test-results/test`. Полный набор также запускает Java- и Kotlin-проверки приложения с этой же тестовой базой.

## 5. Результаты BL-06

Проверено 11.11.2026 в ветке `feature-c/postgresql-migrations` на основе `2b8af0e`, до коммита текущего этапа. Окружение: Windows, Java 25, Docker Engine 28.4.0, Linux/amd64, PostgreSQL 18.6. Использован образ `postgres:18.6` с digest `sha256:e3d24f6906d0760bf4da0dae872415391ededefad23fd471c47dc53b0ddf3c42`.

| Проверка | Фактический результат |
|---|---|
| `spotlessApply clean build --write-locks` | Успешно, новые зависимости закреплены |
| Повторный `clean build` без обновления lock-файла | Успешно, 61 выполнение, ошибок и пропусков нет |
| `DatabaseMigrationTest` | 12 тестовых методов, 59 выполнений с параметризованными вариантами, все успешны |
| Первый запуск собранного JAR на пустой базе | Применены V1 и V2, четыре категории, health и readiness возвращают `200` и `UP` |
| Второй запуск того же JAR на той же базе | Новых миграций нет, полные записи категорий и истории Flyway совпадают с первым запуском, health и readiness возвращают `200` и `UP` |

Для проверки JAR использовались отдельный временный контейнер PostgreSQL и случайные локальные порты. После двух запусков процессы приложения остановлены, проверочный контейнер удалён. Обычная локальная база из README не создавалась и не изменялась.

Локальные свидетельства: `build/database-startup-1.log`, `build/database-startup-2.log`, `build/database-startup-verification.json`, XML и HTML JUnit. Каталог `build` не включается в Git и удаляется задачей `clean`; итог проверки сохранён в этой таблице.

Связь с тест-планом: IT-01 выполнен; IT-15 выполнен в части ограничений SQL, его проверка соответствия API остаётся впереди. Запуски на параметрах не заменяют требуемое разнообразие бизнес-тестов. Compose, резервное копирование, восстановление и доставка в этом этапе не проверялись.
