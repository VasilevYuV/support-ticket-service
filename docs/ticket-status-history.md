# Переходы статуса и история

**Автор:** Васильев Юрий, 4П1.23

На BL-10 реализованы `PATCH /api/tickets/{id}/status` и `GET /api/tickets/{id}/history`. На момент BL-10 были доступны шесть из восьми бизнес-операций. На BL-11 добавлен [поиск](ticket-search.md); Kotlin-отчёт остаётся в плане. Миграции и версии зависимостей не менялись.

## 1. Контракт

Тело перехода содержит только обязательный статус:

```json
{"status":"IN_PROGRESS"}
```

Разрешены четыре пары: NEW -> IN_PROGRESS, NEW -> CANCELLED, IN_PROGRESS -> RESOLVED, IN_PROGRESS -> CANCELLED. Остальные 12 пар, включая повтор текущего состояния, дают `409 STATE_CONFLICT`. Прямое завершение NEW запрещено. При завершении и отмене заполняется `closedAt`; при переходе в работу оно остаётся null.

Успешный переход возвращает `200` с полным Ticket. Поля заявки, кроме статуса, времени закрытия и вычисляемой просрочки, не меняются. Терминальная заявка не считается просроченной. Повтор PATCH после неопределённого сетевого результата может дать `409`, поэтому клиент сначала проверяет текущее состояние и историю.

Неизвестное имя, null, пропуск статуса, неверный JSON-тип, неизвестное поле или параметр дают `400` до поиска заявки. Для корректного запроса отсутствующая заявка даёт `404`. Используются [общие правила JSON и UUID](request-validation.md).

История возвращается массивом по `id ASC`. Каждая запись содержит только `id`, `fromStatus`, `toStatus`, `changedAt`. Для новой заявки результат `[]`, для отсутствующей `404`. Создание и редактирование не добавляют записей истории. Чтение не меняет данные и не включает записи других заявок. Примеры PowerShell находятся в [README](../README.md).

## 2. Структура и транзакция

| Компонент модуля ticket | Назначение |
|---|---|
| `controller.TicketController` | Маршруты перехода и чтения истории |
| `dto.ChangeTicketStatusRequest`, `dto.StatusHistoryResponse` | Отдельные модели запроса и ответа |
| `validation.ChangeTicketStatusRequestDeserializer` | Строгий разбор JSON и имени статуса |
| `validation.TicketRequestValidator` | Проверка обязательного статуса до поиска |
| `service.TicketTransitionPolicy` | Матрица допустимых пар |
| `service.TicketWorkflowService` | Транзакция перехода, общее время и чтение истории |
| `entity.TicketStatusHistory`, `repository.TicketStatusHistoryRepository` | Отображение существующей таблицы и упорядоченная выборка |
| `service.TicketErrors` | Общая ошибка отсутствующей заявки для сервисов |

Переход получает заявку через `findByIdForUpdate` с `PESSIMISTIC_WRITE`, как редактирование. Матрица проверяется после получения блокировки по актуальному состоянию. Затем Clock читается один раз, время усекается до микросекунд. Это значение используется для истории, времени терминального закрытия и расчёта просрочки в ответе.

После изменения сущности вызывается `flush`, чтобы отправить UPDATE заявки в БД до INSERT истории. Оба действия входят в одну транзакцию `TicketWorkflowService.changeStatus`. При сбое INSERT или commit UPDATE тоже откатывается; клиент получает `500`, SQL и стек в ответ не включаются. История не сохраняется отдельной компенсирующей операцией.

При закрытии раньше времени создания ограничение PostgreSQL отклоняет операцию. Время не исправляется автоматически, история не добавляется. Методы чтения выполняются в транзакции только для чтения, DTO формируются до её завершения.

## 3. Проверки

```powershell
.\gradlew.bat test --tests '*TicketWorkflowServiceTest' --tests '*TicketWorkflowApiTest' --tests '*TicketWorkflowConcurrencyTest'
```

Модульные тесты используют настоящие сущность, валидатор и mapper с Mockito-репозиториями и Clock. Проверяются четыре разрешённые пары, двенадцать запрещённых, отсутствие побочных действий при отказе, однократное чтение времени после блокировки, одна запись истории и передача ошибок сохранения к транзакционной границе. Такой тест передачи исключения сам по себе не доказывает rollback.

HTTP-тесты работают с PostgreSQL 18.6 через Testcontainers. Начальные состояния создаются через действующий API переходов. Результат проверяется независимым чтением таблиц после ответа. Покрыты матрица, время и порядок истории, неизменность остальных данных, пустая история, изоляция заявок, некорректные тела, UUID, параметры и тип содержимого.

В тесте rollback на таблицу истории временно добавляется ограничение, запрещающее RESOLVED. Сервис сначала выполняет UPDATE заявки, затем INSERT завершается ошибкой. После ответа `500` полный снимок заявки и прежняя история совпадают с исходными. Ограничение удаляется в `finally`; повторный переход успешно добавляет ровно одну запись. Отдельно проверен откат при часах раньше создания.

## 4. Конкурирующие запросы

В `TicketWorkflowConcurrencyTest` временный триггер задерживает первый UPDATE после блокировки строки на PostgreSQL advisory lock. Отдельное соединение управляет этой задержкой. Через `pg_blocking_pids` сначала подтверждается ожидание первого запроса, затем ожидание второго на строке первого. Только после этого задержка снимается. Это фиксирует порядок двух реальных HTTP-операций без случайного предположения о порядке потоков.

| Сценарий | Проверенный результат |
|---|---|
| RESOLVED раньше CANCELLED | Первый ответ `200`, второй `409`, одна новая история |
| CANCELLED раньше RESOLVED | Первый ответ `200`, второй `409`, одна новая история |
| Закрытие раньше редактирования | `200` и `409`; исходные редактируемые данные сохранены |
| Редактирование раньше закрытия | Оба ответа `200`; новые данные сохранены в закрытой заявке |

Каждая операция использует отдельную транзакцию. Временные триггер, функция и блокировки снимаются в `finally`; в рабочую схему они не входят. Искусственный сбой INSERT и тестовая задержка не считаются найденными дефектами приложения.
