# HTTP-отчёт и источник PostgreSQL

**Автор:** Васильев Юрий, 4П1.23

На BL-13 подключён `GET /api/reports/summary`: Java-контроллер вызывает Kotlin-сервис расчёта, который получает данные из PostgreSQL через Java-интерфейс ReportDataSource. Реализованы все восемь бизнес-маршрутов. Это не означает завершения этапов E2E, покрытия, эксплуатации и CI/CD.

## 1. Запрос

```http
GET /api/reports/summary?from=2026-11-01T00:00:00Z&to=2026-11-02T00:00:00Z
```

Обе границы обязательны. Принимаются строгие даты со смещением или Z и точностью до шести дробных знаков. Границы нормализуются в UTC; from должен быть строго раньше to. Знак `+` смещения передаётся как `%2B`, пример PowerShell с EscapeDataString находится в [README](../README.md).

| Условие | Ответ |
|---|---|
| Корректный период | `200`, SummaryReport с семью полями |
| Нет from или to | `400 VALIDATION_ERROR`, нарушение соответствующего поля |
| Неверная дата, пустое или повторное значение, неизвестный параметр | `400 INVALID_REQUEST` с именем поля |
| from >= to | `400 VALIDATION_ERROR`, нарушение period |
| Неподдерживаемый метод | `405 METHOD_NOT_ALLOWED` |
| Несовместимый Accept | `406 NOT_ACCEPTABLE` в общем JSON-формате |

В выборку входят заявки с `from <= createdAt < to`. Фильтр использует время создания, а не закрытия. Состояния берутся текущие. В ответе присутствуют все четыре статуса и три приоритета, включая нули; среднее явно равно null, если решённых заявок нет. Пустая выборка даёт `200`, а не `404`. Формулы приведены в [описании расчёта](report-calculation.md).

## 2. Устройство кода

| Компонент report | Ответственность |
|---|---|
| `controller.ReportController` | Приём from/to и вызов Kotlin-сервиса |
| `validation.ReportPeriodParser` | Обязательные границы и разбор через общий ApiDateTime |
| `dto.ReportPeriod` | Проверенные значения Instant |
| `service.SummaryReportService` | Spring-компонент на Kotlin, проверка порядка периода и все расчёты |
| `repository.JpaReportDataSource` | Один JPQL-запрос к PostgreSQL, реализующий ReportDataSource |

Источник использует constructor projection в Java-record ReportTicket. Выбираются только status, priority, createdAt, dueAt и closedAt. Параметры периода связываются через setParameter. Сущности Ticket, категории и история не загружаются; ленивые связи не передаются в Kotlin.

Запрос источника выполняется в транзакции только для чтения. После её завершения Kotlin рассчитывает показатели по полученному списку. Все данные отчёта относятся к одной выборке; для каждого счётчика отдельного SQL нет. Контрольный момент просрочки читается один раз в сервисе, как проверено на BL-12.

Проверки синтаксиса, наличия границ и порядка периода проходят до вызова источника. ReportController не обращается к репозиторию напрямую. Миграции, схема и версии зависимостей на BL-13 не менялись.

## 3. Проверки

```powershell
.\gradlew.bat test --tests '*ReportPeriodParserTest' --tests '*SummaryReportApiTest'
```

ReportPeriodParserTest проверяет отсутствие обеих или одной границы, нормализацию смещения, сохранение микросекунд и отказ для неверного формата. Сравнение границ отдельно покрыто Kotlin-тестами сервиса.

SummaryReportApiTest запускает HTTP-приложение и PostgreSQL 18.6 через Testcontainers. Контроллер, Kotlin-сервис и источник настоящие; подменён только Clock для контрольного времени. Статистика Hibernate включена только в этом тестовом контексте. Тест фиксирует один выполненный запрос, один подготовленный SQL statement и отсутствие загрузки JPA-сущностей. Для неверных параметров оба счётчика запросов равны нулю.

В базу загружаются все R1-R8 из [тест-плана](test-plan.md), с согласованной историей состояний. При времени `2026-11-03T00:00:00Z` ответ за `[2026-11-01T00:00:00Z, 2026-11-02T00:00:00Z)` содержит:

- totalCreated=6; NEW=2, IN_PROGRESS=1, RESOLVED=2, CANCELLED=1.
- LOW=2, MEDIUM=2, HIGH=2; обе суммы равны totalCreated.
- openOverdue=1; срок на точной границе не считается просроченным.
- averageResolutionSeconds=7200; R4 учитывается при закрытии за пределами периода, R6 и R7 исключены по createdAt.

Дополнительно проверены пустая выборка, отсутствие RESOLVED, период длиной в одну микросекунду, эквивалентные смещения, UTC в ответе, отсутствие и повторы параметров, неизвестное имя, лишняя точность, неверная календарная дата, границы года, raw `+`, метод и Accept. Полные снимки таблиц заявок и истории после чтения совпадают с исходными.
