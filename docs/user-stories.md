# Пользовательские истории и критерии приёмки

**Автор:** Васильев Юрий, 4П1.23

Основание: [постановка задачи и требования](requirements.md). Приоритеты и порядок реализации приведены в [backlog](backlog.md).

Критерии описывают ожидаемое поведение, а не результаты выполненных тестов. Обозначение `AC-XX.Y` связывает критерий с историей `US-XX`; эти идентификаторы будут использованы в тест-плане. В сценариях изменения данных сравниваются сохранённые значения до и после операции.

## US-01. Выбор категории

Как сотрудник, регистрирующий обращение, я хочу получить справочник категорий, чтобы отнести заявку к нужному направлению поддержки.

**Связь с требованиями:** FR-07, BR-01.

- **AC-01.1.** При запросе справочника API возвращает HTTP `200` и список категорий с идентификаторами и названиями.
- **AC-01.2.** Идентификатор категории из справочника принимается при создании заявки; сохранённая заявка связана именно с этой категорией.
- **AC-01.3.** При отсутствии категории или передаче неизвестного идентификатора категории создание отклоняется с HTTP `400`; новая заявка не появляется в базе.

## US-02. Регистрация обращения

Как сотрудник, регистрирующий обращение, я хочу создать заявку с заголовком, описанием, категорией, приоритетом и сроком, чтобы обращение было учтено.

**Связь с требованиями:** FR-01, FR-09, BR-01, BR-02, BR-03, BR-09, NFR-04.

- **AC-02.1.** При корректных данных API возвращает HTTP `201` и созданную заявку с уникальным идентификатором, переданными значениями, статусом `NEW` и временем создания; время закрытия равно `null`.
- **AC-02.2.** Каждый из приоритетов `LOW`, `MEDIUM`, `HIGH` принимается и сохраняется без подмены значения.
- **AC-02.3.** Отсутствующий, пустой или состоящий только из пробелов заголовок приводит к HTTP `400`; количество заявок не изменяется.
- **AC-02.4.** Неизвестное значение приоритета приводит к HTTP `400` в общем формате ошибок; заявка не сохраняется.
- **AC-02.5.** После успешного создания заявка доступна по полученному идентификатору и содержит сохранённые данные.

## US-03. Просмотр заявки

Как сотрудник, я хочу получить заявку по идентификатору, чтобы узнать её данные и текущее состояние.

**Связь с требованиями:** FR-02, BR-09, NFR-04.

- **AC-03.1.** Для существующей заявки API возвращает HTTP `200`, идентификатор, заголовок, описание, категорию, приоритет, статус, время создания, срок и время закрытия.
- **AC-03.2.** Для корректного по формату, но отсутствующего идентификатора API возвращает HTTP `404` в общем формате ошибок.
- **AC-03.3.** Чтение не изменяет поля заявки и её историю; завершённые и отменённые заявки остаются доступными для чтения.

## US-04. Уточнение данных

Как специалист технической поддержки, я хочу изменить описание, приоритет или срок открытой заявки, чтобы уточнить условия её выполнения.

**Связь с требованиями:** FR-03, FR-09, BR-02, BR-06, BR-09.

- **AC-04.1.** Для заявок в состояниях `NEW` и `IN_PROGRESS` разрешённые изменения сохраняются и видны при повторном чтении.
- **AC-04.2.** Изменение описания, приоритета или срока не меняет идентификатор, время создания, статус и историю статусов.
- **AC-04.3.** Редактирование завершённой или отменённой заявки возвращает HTTP `409`; все её поля и история остаются прежними.
- **AC-04.4.** Некорректный приоритет возвращает HTTP `400`, отсутствующая заявка - HTTP `404`; частичные изменения не сохраняются.

## US-05. Выполнение заявки

Как специалист технической поддержки, я хочу перевести заявку в работу и затем завершить её, чтобы отражать ход решения обращения.

**Связь с требованиями:** FR-04, FR-05, BR-04, BR-06, BR-07, BR-09, BR-10.

- **AC-05.1.** Для заявки `NEW` переход в `IN_PROGRESS` успешно сохраняет новое состояние и одну запись о переходе в истории.
- **AC-05.2.** Для заявки `IN_PROGRESS` переход в `RESOLVED` сохраняет новое состояние, время закрытия и одну запись о переходе в истории.
- **AC-05.3.** Попытки переходов `NEW` → `RESOLVED`, `IN_PROGRESS` → `NEW` и повторного открытия `RESOLVED` возвращают HTTP `409`; поля заявки и история не меняются.
- **AC-05.4.** Полный сценарий создания, перевода в работу и завершения заканчивается состоянием `RESOLVED`; история содержит оба успешных перехода в правильном порядке.

## US-06. Отмена обращения

Как специалист технической поддержки, я хочу отменить неактуальную открытую заявку, чтобы исключить её из текущей работы без удаления данных.

**Связь с требованиями:** FR-04, FR-05, BR-05, BR-06, BR-07, BR-10.

- **AC-06.1.** Отмена из `NEW` и из `IN_PROGRESS` сохраняет состояние отмены и соответствующую запись истории.
- **AC-06.2.** Отмена из `RESOLVED` отклоняется с HTTP `409`; состояние, время закрытия и история остаются прежними.
- **AC-06.3.** Попытка перевести отменённую заявку в `NEW`, `IN_PROGRESS` или `RESOLVED` возвращает HTTP `409` без изменения данных.
- **AC-06.4.** Отменённая заявка с истёкшим сроком не включается в число открытых просроченных заявок.

Состояние отмены называется `CANCELLED`; при отмене заполняется время закрытия. Основания приведены в [правилах обработки заявки](ticket-workflow.md).

## US-07. Сохранение истории

Как специалист технической поддержки, я хочу иметь достоверную историю смены статусов, чтобы восстановить последовательность обработки заявки.

**Связь с требованиями:** FR-05, BR-07, BR-10.

- **AC-07.1.** Для каждого успешного перехода сохраняется запись, связанная с заявкой и содержащая предыдущее состояние, новое состояние и время изменения.
- **AC-07.2.** При искусственно вызванной в интеграционном тесте ошибке сохранения истории откатывается и изменение состояния заявки; незавершённый переход не остаётся в базе.
- **AC-07.3.** Отклонённая операция не добавляет записи в историю, не меняет существующие записи и состояние заявки.
- **AC-07.4.** После перезапуска приложения сохранённые записи истории доступны для проверки в базе и соответствуют выполненным переходам.

Проверка хранения истории не требует отдельного пользовательского интерфейса. Предусмотрен отдельный метод чтения истории по идентификатору заявки; точный маршрут и схема ответа будут определены в контракте. У новой заявки история пуста.

## US-08. Поиск и контроль сроков

Как специалист технической поддержки, я хочу получать страницы заявок по выбранным условиям, чтобы находить обращения и контролировать просрочку.

**Связь с требованиями:** FR-06, FR-08, BR-08, NFR-08.

- **AC-08.1.** Фильтрация по статусу, приоритету и категории возвращает только соответствующие заявки; при сочетании фильтров выполняются все заданные условия.
- **AC-08.2.** Фильтр просрочки выбирает только заявки `NEW` и `IN_PROGRESS` со сроком строго раньше контрольного момента времени.
- **AC-08.3.** При времени, равном сроку, заявка ещё не просрочена; после срока открытая заявка просрочена. Завершённые и отменённые заявки исключены из просроченных при любом сроке.
- **AC-08.4.** При неизменных данных последовательные страницы с фиксированным размером и определённым контрактом порядком не дублируют и не пропускают записи. Ответ содержит сведения, позволяющие определить общее количество подходящих заявок.
- **AC-08.5.** При отсутствии совпадений API возвращает HTTP `200`, пустую страницу и нулевое общее количество; неверные параметры пагинации или фильтра возвращают HTTP `400`.

## US-09. Статистика за период

Как руководитель технической поддержки, я хочу получить сводку по заявкам, созданным за период, чтобы оценить их состояние и время решения.

**Связь с требованиями:** FR-10, FR-08, BR-08, KR-01, KR-02, KR-03, KR-04, KR-05, KR-06, KR-07, NFR-08.

- **AC-09.1.** `GET /api/reports/summary` с корректным периодом возвращает HTTP `200`, количество созданных заявок, распределение по текущим статусам и приоритетам, количество открытых просроченных и среднее время решения.
- **AC-09.2.** Все показатели используют заявки с временем создания `from <= createdAt < to`: запись на границе `from` включается, на границе `to` исключается. Записи вне периода не влияют ни на один показатель.
- **AC-09.3.** Сумма количеств по статусам и сумма количеств по приоритетам каждая равна общему количеству выбранных заявок. Статусы берутся на момент формирования отчёта.
- **AC-09.4.** В просрочку входят только открытые заявки выбранной совокупности со сроком раньше контрольного времени. Весь расчёт использует один контрольный момент.
- **AC-09.5.** Для двух решённых заявок с длительностями 1 и 3 часа среднее равно 2 часам в единице измерения, определённой контрактом. Отменённые и открытые заявки не участвуют в среднем; решённая заявка учитывается и при закрытии за пределами периода, если её создание попало в период.
- **AC-09.6.** При отсутствии `RESOLVED` среднее равно `null`. Для пустой выборки общее количество и количество просроченных равны нулю, распределения не содержат ненулевых значений, среднее равно `null`.
- **AC-09.7.** Отсутствующие или некорректные границы периода, а также `from >= to`, возвращают HTTP `400` в общем формате ошибок.
- **AC-09.8.** Рабочий маршрут отчёта вызывает расчёт на Kotlin с моделями `data class`, nullable-значением среднего и операциями над коллекциями. Взаимодействие Java и Kotlin подтверждается кодом, успешным запросом и минимум тремя Kotlin-тестами, один из которых проверяет Java-компонент; отчёт объясняет два решения, обусловленных Kotlin.

## US-10. Воспроизводимый запуск

Как ответственный за эксплуатацию, я хочу запустить сервис по инструкции, чтобы получить рабочее приложение с готовой базой данных.

**Связь с требованиями:** NFR-01, NFR-02, NFR-03, NFR-05, NFR-06.

- **AC-10.1.** На окружении с документированными предварительными условиями чистая копия проекта запускается командами README после заполнения локальных переменных окружения; готовность базы и приложения подтверждается health checks, запрос к API завершается успешно.
- **AC-10.2.** На пустой базе автоматически применяются миграции. Повторный запуск не создаёт повторные таблицы или записи миграций и не удаляет заявки.
- **AC-10.3.** После перезапуска контейнеров с сохранением тома созданная заявка и её история доступны и совпадают с данными до перезапуска.
- **AC-10.4.** Dockerfile содержит отдельные этапы сборки и запуска; Compose определяет приложение, PostgreSQL, постоянный том и проверки готовности. Логи доступны через стандартные средства просмотра логов контейнера.
- **AC-10.5.** В `.env.example` присутствуют имена необходимых параметров без реальных секретов. Реальные значения отсутствуют в отслеживаемых файлах; параметры CI/CD поступают из секретов платформы.

## US-11. Восстановление и диагностика

Как ответственный за эксплуатацию, я хочу сохранить резервную копию, проверить восстановление и иметь порядок диагностики, чтобы восстановить сервис после сбоя.

**Связь с требованиями:** NFR-02, NFR-06, NFR-07; раздел 9 требований.

- **AC-11.1.** Команда из инструкции создаёт резервную копию базы с демонстрационными заявками и историей; команда завершается успешно, а файл копии существует.
- **AC-11.2.** Копия восстанавливается в отдельную тестовую базу; состав таблиц, количество и значения контрольных записей заявок, категорий и истории совпадают с исходным набором. Исходная база не изменяется.
- **AC-11.3.** Инструкция для недоступной базы содержит команды проверки состояния контейнера, подключения и журналов; для неуспешного health check приложения - проверки состояния и логов приложения; для ошибки миграции - проверки ошибки и истории миграций.
- **AC-11.4.** Для каждой из трёх ситуаций описаны признаки, последовательность проверки и действия восстановления. Команды проверены в изолированном тестовом окружении, результаты записаны в отчёте.

## US-12. Проверяемая доставка и откат

Как ответственный за эксплуатацию, я хочу автоматически доставлять проверенную версию на стенд и возвращаться к предыдущей, чтобы контролировать выпуск приложения.

**Связь с требованиями:** NFR-01, NFR-03, NFR-05; раздел 9 требований.

- **AC-12.1.** Для pull request pipeline проверяет форматирование или выполняет статический анализ Java и Kotlin, собирает приложение, запускает автоматизированные тесты, публикует отчёты тестирования и покрытия, собирает образ; развёртывание не выполняется.
- **AC-12.2.** После успешного слияния в основную ветку pipeline публикует образ с тегом по SHA коммита, запускает именно этот образ на учебном стенде и выполняет health check и проверочный запрос к API.
- **AC-12.3.** При провале тестов публикация образа и развёртывание не запускаются; блокировка подтверждена результатом отдельного проверочного запуска pipeline.
- **AC-12.4.** При неуспешной проверке приложения после развёртывания pipeline отмечает доставку как неуспешную.
- **AC-12.5.** На стенде выполнен возврат к предыдущему образу: идентификатор запущенного образа соответствует выбранной предыдущей версии, health check и проверочный запрос успешны, сохранённые заявки доступны. Схема базы совместима с предыдущей версией.
- **AC-12.6.** В материалах сдачи есть ссылка на успешный pipeline, идентификатор развёрнутого образа, результаты проверки приложения и отката. Публикация образа без работающего приложения не принимается как завершённый результат.

## Общие условия приёмки

- Все ответы с HTTP `400`, `404`, `409` соответствуют единой схеме ошибки, которая будет закреплена в контракте API.
- Тест-план связывает требования и перечисленные критерии с конкретными проверками: минимум 10 модульных, 6 интеграционных с PostgreSQL через Testcontainers и 2 сквозных сценария.
- Проверки времени используют управляемый `Clock` и фиксированные данные, не зависят от системной даты и порядка запуска.
- Отчёт покрытия охватывает бизнес-логику Java и Kotlin; найденные дефекты имеют шаги воспроизведения, хотя бы один исправленный дефект - регрессионный тест.
- Код соответствует NFR-09; инструкции и результаты проверок включены в документацию.
- Для итоговой сдачи выполняются условия раздела 10 требований, включая демонстрацию на защите.

## Уточнения для проектирования

Критерии уточняют исходные требования: успешное создание возвращает `201`, ошибки неизвестной категории - `400`, редактирование закрытой заявки - `409`; заголовок из пробелов недопустим, корректный период требует `from < to`, просрочка наступает строго после срока. Эти решения не меняют обязательные бизнес-правила задания и должны быть перенесены в контракт API.

В [архитектуре](architecture.md) зафиксированы фильтры `status`, `priority`, `categoryId`, `overdue`; страницы с `page=0`, `size=20` по умолчанию и ограничением размера от 1 до 100; порядок `createdAt DESC, id DESC`; время в UTC; среднее время решения в секундах; все группы отчёта, включая нулевые. В [модели данных](data-model.md) определены обязательные поля, значения по умолчанию и допустимость отсутствующего срока. Следующий этап определяет точные JSON-схемы и семантику полей редактирования.
