# Редактирование заявки

**Автор:** Васильев Юрий, 4П1.23

На BL-09 реализован `PUT /api/tickets/{id}/details`. На момент BL-09 были доступны четыре из восьми бизнес-операций. На BL-10 добавлены [смена статуса и HTTP-история](ticket-status-history.md); поиск и отчёт остаются в плане.

## 1. Контракт

```json
{
  "description": "Проверены питание и кабель.",
  "priority": "HIGH",
  "dueAt": null
}
```

Все три поля обязательны. Описание является строкой до 10000 кодовых точек Unicode; пустая строка очищает его. Приоритет принимает LOW, MEDIUM или HIGH. Значение null разрешено только для срока и снимает его. Нормализация срока, точность и строгие JSON-типы соответствуют [общим правилам валидации](request-validation.md). Заголовок, категория и серверные поля в запросе запрещены.

| Условие | Ответ |
|---|---|
| Корректная замена у NEW или IN_PROGRESS | `200`, полный Ticket с пересчитанной просрочкой |
| Пропущено поле, неверные тип, дата, UUID или query-параметр | `400`, единая ошибка API |
| Корректный запрос к отсутствующей заявке | `404 TICKET_NOT_FOUND` |
| Состояние RESOLVED или CANCELLED | `409 STATE_CONFLICT` без изменения данных |
| Неподдерживаемый тип тела | `415 UNSUPPORTED_MEDIA_TYPE` |
| Ошибка сохранения | `500 INTERNAL_ERROR`, транзакция откатывается |

Проверка тела выполняется до поиска заявки. Повтор идентичного запроса к открытой заявке допустим. Операция не меняет UUID, заголовок, категорию, статус, время создания, время закрытия и историю. Пример PowerShell приведён в [README](../README.md).

## 2. Структура и транзакция

В модуле `ticket` добавлены DTO `ReplaceTicketDetailsRequest` и его строгий десериализатор. Общий `TicketRequestValidator` проверяет создание и редактирование; правило длины описания используется обоими методами. Он заменил прежний `CreateTicketValidator`.

Контроллер разбирает UUID и вызывает `TicketService.replaceDetails`. Сервис проверяет поля, затем получает сущность через `TicketRepository.findByIdForUpdate` с блокировкой `PESSIMISTIC_WRITE`. После получения блокировки проверяется актуальный статус. Метод сущности `replaceDetails` меняет только три разрешённых поля; JPA сохраняет изменения при завершении транзакции. DTO формируется внутри неё. Ошибка сохранения не превращается в успешный HTTP-ответ.

Блокировка удерживается до commit или rollback. Если другая транзакция успела закрыть заявку, ожидавшее редактирование получает новое состояние и возвращает `409`. API переходов BL-10 использует ту же блокировку строки. Конкурирующие успешные редактирования последовательно заменяют весь набор полей; ETag не используется. Механизм объявления блокировки описан в [Spring Data JPA](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html).

Схема, миграции, зависимости и версии инструментов на этом этапе не изменены.

## 3. Проверки

```powershell
.\gradlew.bat test --tests '*TicketDetailsServiceTest' --tests '*TicketDetailsApiTest'
```

`TicketDetailsServiceTest` проверяет оба открытых и оба терминальных состояния, замену и очистку данных, валидацию до обращения к репозиторию и отсутствие заявки. Используются настоящий валидатор, mapper и сущность; репозиторий заменён Mockito. Состояния заданы тестовой подменой чтения статуса, без добавления публичного setter в сущность.

`TicketDetailsApiTest` отправляет HTTP-запросы приложению с PostgreSQL 18.6 через Testcontainers. Проверяются:

- Замена в NEW и IN_PROGRESS, чтение сохранённого результата и повтор PUT.
- Очистка срока и описания, все приоритеты, Unicode-описание предельной длины.
- Неверные и пропущенные поля, запрещённые поля, формат UUID, неизвестная заявка и порядок валидации.
- Полная неизменность заявки и истории при отказе, сохранность неизменяемых полей при успешной замене.
- Откат всех редактируемых полей при искусственном ограничении PostgreSQL, запрещающем обновление.
- Ожидание блокировки и повторная проверка состояния после её освобождения.

В последней проверке отдельное JDBC-соединение удерживает `FOR UPDATE`, затем запускается HTTP-запрос. Через `pg_blocking_pids` подтверждается реальное ожидание. Блокирующая транзакция переводит заявку в CANCELLED и добавляет историю через SQL, после commit редактирование получает `409`. Это проверка защиты редактирования, а не API переходов, который на BL-09 ещё не был реализован. Ожидание ограничено по времени, произвольная задержка не заменяет подтверждение блокировки.

Для остальных состояний тестовые данные также подготавливаются SQL. Временное ограничение сбоя удаляется в `finally`. Эти искусственные сценарии не считаются найденными дефектами приложения.

Связь с планом: UT-03, UT-14, IT-05 выполнены; IT-04, IT-07, IT-13 и IT-14 дополнены в указанном объёме. Переходы статусов и их конкуренция проверены отдельно на BL-10. Сквозные сценарии и оставшиеся операции ещё не проверены.
