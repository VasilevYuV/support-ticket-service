# Swagger UI, коллекция запросов и демонстрационные данные

**Автор:** Васильев Юрий, 4П1.23

## 1. Документация работающего API

После запуска приложения доступны:

- `/swagger-ui.html`: Swagger UI, перенаправление на `/swagger-ui/index.html`.
- `/openapi.yaml`: контракт всех восьми бизнес-операций.
- `/v3/api-docs/swagger-config`: настройки интерфейса.

Единственный исходник спецификации - [openapi.yaml](openapi.yaml). Gradle копирует его в static при processResources и в contract при processTestResources. Ручной второй копии нет. Swagger UI настроен на `/openapi.yaml`; генерация альтернативного документа `/v3/api-docs` отключена через `springdoc.enable-default-api-docs: false`, при этом настройки UI доступны. Это сохраняет явно заданные правила строгого JSON и ошибок, которые нельзя полностью вывести из сигнатур Java.

В спецификации указан сервер `/`, поэтому Try it out обращается к текущему адресу и порту приложения. В интерфейсе видны модули ticket/category/report, примеры, параметры и ответы. Для проверки можно раскрыть GET /api/categories, выбрать Try it out и Execute. Создание и изменения через UI записывают данные в подключённую базу.

Схемы и бизнес-контракт не изменены на BL-20; обновлены описание и адрес сервера. Настройки соответствуют [параметрам springdoc](https://springdoc.org/core-properties.html) и [настройке Swagger UI](https://springdoc.org/). Версия springdoc 3.2.0 закреплена в каталоге, Swagger UI 5.34.0 и транзитивные библиотеки в gradle.lockfile.

## 2. Подготовка отдельной учебной базы

Коллекция требует пустую таблицу заявок и четыре категории из миграции V2. Она создаёт четыре заявки через API, без SQL-вставок, новых миграций или автоматического заполнения при старте приложения. Существующие данные не удаляются. Не запускать демонстрацию на базе с чужими заявками или параллельной записью: точные ожидаемые счётчики относятся к одному учебному запуску.

Пример отдельной локальной PostgreSQL для демонстрации:

```powershell
docker run --rm --name support-demo-postgres -d `
  -e POSTGRES_DB=support_demo `
  -e POSTGRES_USER=support_demo `
  -e POSTGRES_PASSWORD=support_demo_local `
  -p 127.0.0.1:55433:5432 postgres:18.6
docker exec support-demo-postgres pg_isready -U support_demo -d support_demo
```

Дождаться accepting connections. Порт 55433 должен быть свободен. Пароль приведён только для локальной учебной базы. В окне запуска приложения:

```powershell
$env:DB_URL = 'jdbc:postgresql://localhost:55433/support_demo'
$env:DB_USERNAME = 'support_demo'
$env:DB_PASSWORD = 'support_demo_local'
$env:SERVER_PORT = '8080'
.\gradlew.bat bootRun
```

Если порт 8080 занят, выбрать свободный и указать его в baseUrl коллекции. Дождаться готовности `/actuator/health/readiness`. Общие инструкции JDK, сборки и запуска JAR находятся в [README](../README.md).

Этот контейнер запускается без постоянного тома и с --rm. После завершения демонстрации сначала остановить приложение через Ctrl+C, затем `docker stop support-demo-postgres`. Учебные записи будут удалены вместе с контейнером; это не команда очистки обычной базы из README. Для новой демонстрации повторить запуск нового контейнера. Если коллекция прервалась после части записей, также использовать новую пустую учебную базу.

## 3. Postman и Newman

Файлы:

- [Коллекция v2.1](postman/support-service.postman_collection.json).
- [Локальное окружение](postman/local.postman_environment.json).

В Postman импортировать оба файла, выбрать окружение «Практика: локальный API», установить baseUrl без завершающего `/` и запустить всю коллекцию по порядку, одну итерацию. UUID заявок и ID категории сохраняются из ответов в переменные коллекции. ID категорий не заданы числом заранее. Запросы после создания заявок зависят от предыдущих ответов; отправка их в случайном порядке не является проверкой сценария.

Для воспроизводимого запуска нужен Node.js с npm. Проверено на Node.js 24.9.0, npm 11.6.0, Newman 6.2.1. Установка в зависимости приложения не требуется. Команда из корня проекта:

```powershell
npm exec --yes --package=newman@6.2.1 -- newman run `
  docs/postman/support-service.postman_collection.json `
  -e docs/postman/local.postman_environment.json `
  --env-var baseUrl=http://localhost:8080 `
  --bail --timeout-request 10000 `
  --reporters cli,json,junit `
  --reporter-json-export build/api-demo/newman.json `
  --reporter-junit-export build/api-demo/newman.xml
```

Первый запуск загружает Newman из npm registry. Параметры и отчёты описаны в [документации Newman](https://github.com/postmanlabs/newman). Код 0 означает успешный прогон, код 1 - ошибку проверки или запроса. `--bail` останавливает прогон после ошибки. При заполненной базе второй запрос проверяет totalElements, останавливает коллекцию и выдаёт явную ошибку до любых POST/PUT/PATCH. Эта проверка не обеспечивает блокировку конкурентных клиентов.

Коллекция не содержит секретов. Демонстрационные payload находятся непосредственно в четырёх POST-запросах, это источник учебного набора. Для воспроизведения не требуется вручную переносить UUID или загружать SQL.

## 4. Набор и ожидаемые результаты

Все заявки относятся к категории «Оборудование», ID читается из справочника. В описании учебных записей указан автор; описание первой заявки затем изменяется через PUT.

| Заявка | Итоговый статус | Приоритет | Срок | История |
|---|---|---|---|---|
| Не работает принтер | NEW | HIGH | 2000-01-01T00:00:00Z | Пустая |
| Требуется настройка рабочего места | IN_PROGRESS | MEDIUM | null | NEW -> IN_PROGRESS |
| Замена кабеля принтера | RESOLVED | LOW | null | NEW -> IN_PROGRESS -> RESOLVED |
| Повторное обращение | CANCELLED | MEDIUM | null | NEW -> CANCELLED |

UUID, createdAt, closedAt и время истории формирует приложение. Для современного контрольного времени первая заявка просрочена. Среднее время решения не задано фиксированной константой: оно определяется реальными временами создания и закрытия третьей заявки, сверяется с ними с допуском 0,001 секунды из-за миллисекундной точности JavaScript Date. Точные микросекунды проверяются отдельными Kotlin/HTTP-тестами приложения.

Отчёт за `[0001-01-01T00:00:00Z, 9999-12-31T23:59:59Z)` должен дать totalCreated=4, по одному статусу, LOW=1/MEDIUM=2/HIGH=1 и openOverdue=1. Среднее неотрицательно. Фильтр NEW + HIGH + categoryId + overdue=true возвращает только первую заявку, одну страницу.

| Операция API | Запросы коллекции |
|---|---|
| GET /api/categories | 01 |
| POST /api/tickets | 03-06 |
| GET /api/tickets/{id} | 07, 17, 19, 20 |
| PUT /api/tickets/{id}/details | 08 |
| PATCH /api/tickets/{id}/status | 09-12, 16 |
| GET /api/tickets/{id}/history | 13, 18 |
| GET /api/tickets | 02, 14 |
| GET /api/reports/summary | 15, 21 |

Проверяются коды 200/201/400/404/409, Location, значения полей, переходы, история, фильтры и статистика. После запрещённого перехода третьей заявки сравниваются полное тело заявки и весь массив истории с сохранёнными снимками. Ошибка UUID, отсутствие заявки и неверный период имеют отдельные ожидания. Коллекция содержит 21 HTTP-запрос и 42 именованные проверки; внутри одной проверки могут быть несколько утверждений. Она не подменяет JUnit-набор и не добавляет 42 новых бизнес-сценария.
