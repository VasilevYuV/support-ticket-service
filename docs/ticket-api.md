# API категорий и создания заявок

**Автор:** Васильев Юрий, 4П1.23

На BL-07 реализованы три операции [контракта](api-contract.md): `GET /api/categories`, `POST /api/tickets`, `GET /api/tickets/{id}`. На BL-09 добавлено [редактирование заявки](ticket-details.md). На BL-10 добавлены [переходы статуса и история](ticket-status-history.md). Поиск и отчёт остаются проектными. Примеры запуска и запросов приведены в [README](../README.md).

## 1. Структура

| Пакет | Ответственность |
|---|---|
| `category.controller`, `category.service`, `category.repository` | Чтение справочника по возрастанию ID и поиск категории для создания |
| `category.entity`, `category.dto` | JPA-сущность категории и отдельный ответ API |
| `ticket.controller`, `ticket.service`, `ticket.repository` | HTTP, транзакция создания и чтение заявки |
| `ticket.entity`, `ticket.dto` | JPA-сущность, enum, модель запроса и ответ |
| `ticket.validation` | Основные проверки полей создания до обращения к базе |
| `ticket.mapper` | Формирование ответа внутри транзакции, включая данные категории |
| `ticket.service.TicketOverduePolicy` | Единое Java-правило определения просрочки для текущих ответов и будущего Kotlin-отчёта |
| `common.error` | Ошибка API, нарушения полей и общий обработчик поддерживаемых исключений |

Контроллеры не обращаются к репозиториям. `TicketService` получает категорию через `CategoryService`, сохраняет заявку и формирует DTO внутри транзакции. Связь категории загружается лениво; сериализация ответа не обращается к JPA. `open-in-view` остаётся выключенным.

Сущности проверяются Hibernate с `ddl-auto: validate`. Миграции V1 и V2 не менялись, дополнительных таблиц на этом этапе нет. Сущность истории добавлена на BL-10 вместе с операциями перехода и чтения истории.

## 2. Создание и чтение

UUID генерируется на стороне приложения средствами JPA. Конструктор заявки устанавливает `NEW`; время создания берётся из `Clock` и усекается до микросекунд. Заголовок проверяется до очистки краёв, затем сохраняется без краевых пробелов. Для отсутствующих или null полей описания и приоритета используются пустая строка и `MEDIUM`. Срок и время закрытия могут быть null.

Ответ создания содержит `Location: /api/tickets/{id}`. В ответах присутствуют все десять полей Ticket, включая явные null. Категория содержит ID и название. Новая заявка не создаёт запись истории. Повторный POST создаёт новую заявку с другим UUID.

Чтение работает для всех четырёх статусов. `overdue` вычисляется для `NEW` и `IN_PROGRESS`, только при непустом сроке строго раньше контрольного времени. На точной границе срока результат false; у терминальных заявок false независимо от срока. Поле не хранится в PostgreSQL.

## 3. Валидация

На BL-07 добавлены проверки обязательных полей, длины строк, категории и основные ответы `400/404`. На BL-08 реализованы строгие JSON-типы, даты до преобразования в Instant, канонический формат UUID, запрет неизвестных и повторных query-параметров и единые ошибки HTTP. Подробные правила и результаты находятся в [описании валидации](request-validation.md).

Редактирование реализовано на BL-09. Статусы и HTTP-история реализованы на BL-10; поиск и отчёт ещё не реализованы. Проверки ниже описывают исходный набор BL-07; актуальное состояние сценариев указано в [тест-плане](test-plan.md).

## 4. Проверки

```powershell
.\gradlew.bat test --tests '*TicketApiTest'
```

Тест запускает HTTP-сервер и PostgreSQL 18.6 через Testcontainers. Отдельная тестовая конфигурация заменяет Clock фиксированным значением с наносекундами, чтобы проверить усечение до микросекунд. Тестовые данные очищаются перед каждым вариантом. HTTP-операции не оборачиваются в транзакцию теста; проверка БД видит зафиксированные изменения.

Восемь тестовых методов проверяют:

- список категорий и его порядок;
- создание и чтение полной заявки с каждым из трёх приоритетов, нормализацию смещения времени, Location и отсутствие истории;
- минимальное тело, явные null, значения по умолчанию и разные UUID повторных созданий;
- чтение обеих терминальных заявок без изменения полей и истории;
- срок до, на и после контрольного времени;
- максимальные длины строк с Unicode-символами вне BMP;
- отклонение основных некорректных запросов без изменения числа заявок и истории;
- различие отсутствующей заявки и некорректного UUID, формат ошибок.

Терминальные состояния в тесте чтения подготовлены SQL-запросами. Это проверка чтения уже существующих данных, а не результат работы будущего API переходов.

Связь с тест-планом: IT-02 и IT-03 выполнены в описанном объёме; IT-04 проверен для GET заявки, IT-12 проверен для допустимых смещений и границы просрочки. IT-14 и IT-15 остаются частичными, поскольку другие операции и полный набор ошибок ещё не реализованы.
