# Расчёт отчёта на Kotlin

**Автор:** Васильев Юрий, 4П1.23

На BL-12 подготовлены модели отчёта, Java-интерфейс источника и Kotlin-сервис расчёта. Проверки вызывают сервис напрямую с тестовым источником. Реализация запроса к PostgreSQL, регистрация сервиса в Spring и маршрут `GET /api/reports/summary` относятся к BL-13. Доступными остаются семь бизнес-операций предыдущих этапов.

## 1. Структура модуля report

| Компонент | Язык | Назначение |
|---|---|---|
| `dto.ReportTicket` | Java | Record с текущими статусом, приоритетом и временем создания, срока и закрытия |
| `repository.ReportDataSource` | Java | Интерфейс получения одной выборки по времени создания `[from, to)` |
| `dto.SummaryReport` | Kotlin | Data class результата с Long-счётчиками, распределениями и nullable-средним |
| `service.SummaryReportService` | Kotlin | Проверка порядка границ, общее время и расчёт всех показателей |

Java-модель не содержит JPA-сущностей и ленивых связей. Входные данные источника должны уже соответствовать периоду. Сервис вызывает `findCreatedBetween(from, to)` ровно один раз; отдельных запросов для счётчиков нет. Проверка включения `from` и исключения `to` в SQL выполняется на следующем этапе вместе с реализацией источника.

Сервис проверяет `from < to` до вызова источника и Clock. Ошибка даёт `ApiException` с HTTP-статусом 400 и нарушением `period`; HTTP-обработка этого исключения пока не подключена к отчёту. При корректном периоде Clock читается один раз, время усекается до микросекунд и используется для всех заявок.

## 2. Показатели

- `totalCreated` равен размеру выборки.
- `byStatus` содержит все четыре статуса, `byPriority` все три приоритета, включая нули. Каждая сумма совпадает с totalCreated.
- `openOverdue` использует общий Java-метод `TicketOverduePolicy`: только NEW и IN_PROGRESS, непустой срок строго раньше контрольного времени.
- `averageResolutionSeconds` учитывает только RESOLVED. Время закрытия может быть за пределами периода создания. CANCELLED и открытые заявки не участвуют в среднем.

При пустой выборке счётчики и распределения нулевые, среднее null. При непустой выборке без RESOLVED среднее также null. Отсутствие срока допустимо и не создаёт просрочку. Если источник вернул RESOLVED без времени закрытия или с отрицательной длительностью, расчёт завершается ошибкой данных, а не молча исключает такую заявку.

Для каждой решённой заявки Duration разбивается на целые секунды и наносекундную часть. Их точные BigDecimal-значения суммируются, затем сумма делится на количество решённых с масштабом 6 и HALF_UP. Промежуточного округления нет. Перевод всей длительности в long-наносекунды не используется, чтобы не переполнить число при больших интервалах.

Примеры: 3600 и 10800 секунд дают 7200.000000; длительности 0, 0 и 1 микросекунда дают 0.000000; 0, 1 и 1 микросекунда дают 0.000001. Половина микросекунды округляется до 0.000001.

## 3. Решения, связанные с Kotlin

1. Java-модель помечена `@NullMarked`, а dueAt и closedAt имеют `@Nullable`. Kotlin видит их как допускающие null значения. Результат использует `BigDecimal?`, отсутствие решённых возвращает null, а отсутствие обязательного закрытия проверяется через `checkNotNull`. Оператор `!!` не используется. Поддержка JSpecify описана в [документации Kotlin о Java-взаимодействии](https://kotlinlang.org/docs/java-interop.html#jspecify-support).
2. SummaryReport оформлен как `data class` с val-полями. Распределения получаются через `groupingBy`, `eachCount` и `associateWith`, просрочка через `count`, среднее через `filter` и `fold`. В результат помещаются неизменяемые копии карт. Это сохраняет единый расчёт по коллекции без отдельной SQL-агрегации для каждого показателя.

JSpecify уже присутствует в закреплённых зависимостях сборки; версии и lock-файл не менялись. Расчёт загруженной коллекции соответствует учебному объёму. Производительность на большой базе не измерялась.

## 4. Проверки и результаты

```powershell
.\gradlew.bat test --tests '*SummaryReportServiceTest'
```

Проверено 11.11.2026 в ветке `feature-c/report-calculation` на основе `4a1dd34`, до коммита этапа. Окружение: Windows, Java 25, Kotlin 2.4.21, Docker и PostgreSQL 18.6 для прежних интеграционных тестов.

| Проверка | Результат |
|---|---|
| `spotlessApply build` | Успешно, совместная компиляция Java/Kotlin и оформление пройдены |
| Полный набор | 407 выполнений, 0 ошибок, 0 пропусков |
| `SummaryReportServiceTest` | 10 Kotlin-методов, 14 выполнений с параметризованными вариантами |
| Предыдущие проверки | Все 393 выполнения остаются успешными |

Контрольный тест получает шесть включённых записей R1, R2, R3, R4, R5, R8 из [тест-плана](test-plan.md): totalCreated=6, NEW=2, IN_PROGRESS=1, RESOLVED=2, CANCELLED=1, по два каждого приоритета, openOverdue=1, среднее 7200.000000. Mockito подтверждает один вызов Java-источника с точными границами и одно чтение Clock. Срок на контрольной границе не просрочен даже при наносекундах в исходном Clock.

Дополнительно проверены пустая выборка, отсутствие решённых, закрытие за пределами периода, округление вниз, вверх и половины микросекунды, переход через границу секунды, длительность между годами 0001 и 9999, отсутствие влияния порядка записей и зоны Clock. Некорректный период не вызывает источник; некорректное закрытие не искажает среднее молчаливым пропуском.

На BL-12 выполнены UT-08-UT-11; UT-12 частично выполнен для порядка Instant-границ. Текстовые форматы и отсутствие HTTP-параметров, выборка PostgreSQL и IT-11 пока не проверены. Рабочая HTTP-функция Kotlin и её сквозная интеграция ещё не объявляются завершёнными. Первые попытки сборки остановились на длине строк тестовых данных; после форматирования полный прогон успешен.

Артефакты: `build/test-results/test`, `build/reports/tests/test`. Они не включаются в Git и пересоздаются при сборке. Ручной HTTP-запрос отчёта на этом этапе не выполнялся, поскольку его маршрута пока нет.
