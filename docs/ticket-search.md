**Автор:** Васильев Юрий, 4П1.23

На BL-11 реализован `GET /api/tickets`. Доступны семь из восьми бизнес-операций; Kotlin-отчёт остаётся в плане. Миграции, схема и версии зависимостей не менялись.

## 1. Запрос и ответ

Пример: `GET /api/tickets?status=NEW&priority=HIGH&categoryId=1&overdue=true&page=0&size=20`.

| Параметр | По умолчанию | Допустимые значения |
|---|---|---|
| status | Без фильтра | NEW, IN_PROGRESS, RESOLVED, CANCELLED |
| priority | Без фильтра | LOW, MEDIUM, HIGH |
| categoryId | Без фильтра | От 1 до 9223372036854775807; неизвестная категория даёт пустую страницу |
| overdue | Без фильтра | Только true или false |
| page | 0 | От 0 до 2147483647 |
| size | 20 | От 1 до 100 |

Все фильтры соединяются через AND. Пропуск параметра снимает соответствующий фильтр. Пустое значение не считается пропуском. Числа состоят из цифр `0-9`, без знака, пробелов, дробной части и экспоненты. Имена enum регистрозависимы. Повторы, неизвестные имена, в том числе `sort`, и неверные значения дают `400` с именем поля в `violations`.

Ответ содержит `content`, `page`, `size`, `totalElements`, `totalPages`. В content находятся полные Ticket с категорией, явными null и вычисленной просрочкой. Общее количество учитывает только совпадения фильтров. Число страниц вычисляется округлением вверх без сложения, способного переполнить long.

Для пустой выборки по умолчанию:

```json
{"content": [], "page": 0, "size": 20, "totalElements": 0, "totalPages": 0}
```

Страница за концом непустой выборки тоже пуста, но содержит фактические totalElements и totalPages. Максимальный номер страницы является корректным запросом. Смещение `page * size` вычисляется в long; например, для максимальной страницы и размера 100 оно равно 214748364700.

## 2. Сортировка и просрочка

Порядок фиксирован: `createdAt DESC, id DESC`. Второй ключ обеспечивает однозначный порядок при одинаковом времени создания. UUID сортирует PostgreSQL; тест включает значения по обе стороны старшего бита, чтобы не подменять этот порядок сравнением знаковых чисел Java. Основание выбора уникального порядка описано в [документации PostgreSQL о LIMIT и OFFSET](https://www.postgresql.org/docs/18/queries-limit.html).

`overdue=true` выбирает NEW и IN_PROGRESS с непустым сроком строго раньше контрольного времени. На точной границе срока просрочки нет. `overdue=false` является дополнением: включает открытые заявки на границе и после неё, бессрочные и терминальные заявки с любым сроком.

Clock читается один раз на запрос, время усекается до микросекунд. Один момент используется в SQL-фильтре и при построении всех ответов Ticket. Общий Java-метод `TicketOverduePolicy` остаётся источником вычисляемого поля ответа; его граничные случаи проверены также из Kotlin.

## 3. Структура

| Компонент модуля ticket | Назначение |
|---|---|
| `controller.TicketSearchController` | GET списка и шесть разрешённых query-параметров |
| `validation.TicketSearchParser` | Строгий разбор фильтров, диапазоны и значения по умолчанию |
| `dto.TicketSearchRequest` | Типизированные фильтры и смещение long |
| `service.TicketSearchService` | Общий момент времени, транзакция чтения, DTO страницы |
| `repository.TicketSearchRepository` | Подсчёт совпадений и выборка страницы |
| `dto.TicketPageResponse` | Содержимое страницы и метаданные |

Общий `QueryParameterInterceptor` получает разрешённые имена из аннотаций контроллера. Новые параметры не разрешаются автоматически на POST, переходах или других маршрутах.

Репозиторий составляет условия только из заранее заданных SQL-фрагментов. Пользовательские значения передаются параметрами, а не вставляются в SQL. Один набор условий используется для COUNT и выборки. Если смещение уже за концом результата, выборка не выполняется. Для остальных страниц используются SQL LIMIT и OFFSET с long-смещением; результат отображается в существующую JPA-сущность и преобразуется общим TicketMapper.

Сервис настроен на транзакцию только для чтения с REPEATABLE_READ. COUNT, содержимое и категории читаются в одном снимке PostgreSQL. Между отдельными HTTP-запросами неизменность страниц гарантируется только для неизменных данных. Глубокие страницы могут требовать пропуска большого числа строк; измерения производительности на большой базе на этом этапе не проводились.
