# Проверка запросов и обработка ошибок

**Автор:** Васильев Юрий, 4П1.23

Этап BL-08 дополняет три работающих маршрута: чтение категорий, создание заявки и чтение заявки. Общие проверки используются до обращения к сервисам. На BL-09 эти правила подключены к [редактированию](ticket-details.md). Переходы, история, поиск и отчёт будут подключать их по мере реализации.

## 1. JSON

Тело создания должно быть одним JSON-объектом с полями `title`, `categoryId`, `description`, `priority`, `dueAt`. Повтор одного поля, неизвестное поле, передача серверного поля и дополнительные данные после объекта дают `400 INVALID_REQUEST`.

| Поле | Тип JSON | Проверки |
|---|---|---|
| `title` | Строка | Обязательно, не null, от 1 до 200 кодовых точек до очистки краёв, после очистки не пусто |
| `categoryId` | Целочисленный литерал | Обязательно, не null, положительный int64 существующей категории |
| `description` | Строка или null | До 10000 кодовых точек; null и пропуск превращаются в пустую строку |
| `priority` | Строка или null | Только `LOW`, `MEDIUM`, `HIGH`; null и пропуск дают `MEDIUM` |
| `dueAt` | Строка или null | Дата по правилам ниже; null и пропуск снимают срок |

Число вместо строки, строка вместо ID, дробный или экспоненциальный литерал вместо ID, массив или объект вместо скалярного поля отклоняются. Числовой приоритет не считается номером enum. Типы и формат проверяются до семантической проверки категории.

Длина строки считается в кодовых точках Unicode. С краёв заголовка убираются пробельные символы Java и Unicode-разделители, включая неразрывные пробелы; внутренние пробелы сохраняются. NUL и одиночные UTF-16-суррогаты отклоняются, поскольку их нельзя сохранить как корректный текст PostgreSQL. Корректные суррогатные пары, например emoji, допускаются.

## 2. Даты и UUID

Дата содержит полный календарный день, `T`, часы, минуты, секунды и явное смещение `Z` или `+HH:MM` / `-HH:MM`. Допускается от одного до шести дробных знаков либо отсутствие дробной части. Семь знаков отклоняются даже при завершающем нуле. Проверяется реальный календарь; секунды `60`, час `24`, отсутствие смещения, неверное смещение и краевые пробелы запрещены.

Год исходной даты и нормализованного UTC-момента должен находиться в диапазоне 0001-9999. Это сохраняет единый формат входа, хранения и ответа. Срок в прошлом разрешён. В ответе используется UTC с `Z`.

UUID проверяется как текст из пяти групп `8-4-4-4-12` шестнадцатеричных символов. Регистр букв не влияет на значение. Сокращённые группы, скобки, отсутствие дефисов и прочие символы дают `400` с нарушением поля `id`. Только после успешной проверки выполняется поиск: отсутствующий корректный UUID даёт `404 TICKET_NOT_FOUND`.

## 3. Параметры запроса

У трёх маршрутов BL-08 и PUT details нет query-параметров. Любой переданный параметр отклоняется. `QueryParameterInterceptor` получает список разрешённых имён из `@RequestParam` метода контроллера; он не содержит отдельной копии списка параметров будущих операций. Для разрешённого имени допустимо только одно непустое значение. Проверки диапазонов и значений будущих фильтров добавляются вместе с фильтрами.

Проверка параметров предшествует вызову контроллера и поиску заявки. В ошибке `path` содержит путь без query-строки, а имя неверного параметра находится в `violations`.

## 4. Ошибки

| HTTP | Код | Пример |
|---|---|---|
| 400 | `INVALID_REQUEST` | Неверные JSON, тип, дата, UUID, неизвестное поле или параметр |
| 400 | `VALIDATION_ERROR` | Нет заголовка, превышена длина, категория отсутствует |
| 404 | `TICKET_NOT_FOUND` | Корректный UUID заявки не найден |
| 405 | `METHOD_NOT_ALLOWED` | DELETE для списка категорий; сохраняется заголовок Allow |
| 406 | `NOT_ACCEPTABLE` | Клиент требует неподдерживаемый формат ответа |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Тело POST не имеет типа application/json |
| 500 | `INTERNAL_ERROR` | Ошибка сохранения или другая неожиданная ошибка |

Каждый ответ содержит `timestamp`, `status`, `code`, `message`, `path`, `violations`. При известном неверном поле указывается его имя и сообщение на русском. При неразбираемом теле целиком список нарушений пуст. Время берётся из Clock с точностью микросекунд.

Ответ ошибки формируется как JSON, в том числе при несовместимом Accept. В ответ `500` не включаются SQL, внутреннее исключение и стек. Подробности записываются только в серверный журнал. Ошибки URL вне бизнес-маршрутов не входят в контракт восьми операций.

## 5. Устройство кода

- `ticket.validation.CreateTicketRequestDeserializer` разбирает поля запроса создания.
- `common.json.StrictJsonObject` проверяет объект, разрешённые поля и JSON-типы без неявных преобразований.
- `common.validation.ApiDateTime` и `ApiUuid` разбирают даты и UUID.
- `common.validation.TextValues` очищает пробельные края заголовка.
- `common.validation.QueryParameterInterceptor` проверяет имена и количество query-параметров; подключён через `config.WebConfiguration`.
- `common.error.ApiExceptionHandler` обрабатывает прикладные и стандартные ошибки Spring MVC, сохраняя HTTP-статусы и служебные заголовки.

Разбор JSON выполняется до `TicketRequestValidator` (на BL-08 назывался `CreateTicketValidator`), затем сервис проверяет существование категории и сохраняет заявку. Сущности, схема и версии зависимостей на BL-08 не менялись.
