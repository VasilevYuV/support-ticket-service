## 1. Общие правила

- Планируемый локальный адрес: `http://localhost:8080`. При развёртывании адрес задаётся окружением.
- Тела запросов и ответов используют `application/json` и UTF-8. Авторизация в текущий объём не входит.
- Поля JSON используют `camelCase`. Тело должно быть одним объектом без повторяющихся полей и данных после объекта. Неизвестные поля тела запроса отклоняются с `400`; передавать серверные поля при создании или редактировании нельзя.
- Числовые ID категорий и истории положительные, в пределах знакового `int64`; В JSON ID категории передаётся целочисленным литералом без кавычек, дробной части и экспоненты. ID заявки имеет формат UUID из групп `8-4-4-4-12` шестнадцатеричных символов, регистр букв допускается любой. Неверный формат параметра даёт `400`.
- Строки enum регистрозависимы: приоритет `LOW`, `MEDIUM`, `HIGH`; статус `NEW`, `IN_PROGRESS`, `RESOLVED`, `CANCELLED`.
- Даты имеют вид `2026-11-11T12:00:00+03:00` или `2026-11-11T09:00:00Z`. Допустимо до шести дробных знаков секунды, год от 0001 до 9999 как в исходной записи, так и после перевода в UTC, секунды от 00 до 59. Нет смещения, неверная дата или лишняя точность дают `400`. Ответы используют UTC с `Z`.
- В query-параметре знак `+` смещения передаётся как `%2B`. Для примеров используется `Z`.
- Все перечисленные поля ответа присутствуют; отсутствие срока, времени закрытия или среднего представлено явным `null`.
- Неизвестные query-параметры и повтор одного параметра отклоняются с `400`. Пустое значение заданного параметра не считается его отсутствием. `overdue` принимает только `true` или `false`.
- Проверка синтаксиса, типов и обязательных полей предшествует поиску заявки. Для корректного запроса неизвестный UUID даёт `404`, существующая заявка с запрещённым состоянием даёт `409`.

Проверки существования категории, допустимого перехода, порядка границ периода и согласованности счётчиков являются семантическими. Их нельзя заменить одной проверкой JSON-схемы.

## 2. Перечень методов

| Метод | Путь | Результат | Успех | Истории |
|---|---|---|---|---|
| GET | `/api/categories` | Массив категорий | `200` | US-01 |
| POST | `/api/tickets` | Созданная заявка | `201` | US-02 |
| GET | `/api/tickets/{id}` | Заявка по UUID | `200` | US-03 |
| PUT | `/api/tickets/{id}/details` | Заявка после замены редактируемых полей | `200` | US-04 |
| PATCH | `/api/tickets/{id}/status` | Заявка после перехода статуса | `200` | US-05, US-06 |
| GET | `/api/tickets/{id}/history` | Массив переходов | `200` | US-07 |
| GET | `/api/tickets` | Страница заявок | `200` | US-08 |
| GET | `/api/reports/summary` | Статистика за период | `200` | US-09 |

Методы располагаются в модулях `ticket`, `category`, `report` по схеме `controller -> service -> repository`. OpenAPI-теги соответствуют этим модулям. Эксплуатационные проверки и endpoint готовности будут оформлены при настройке окружения; они не входят в восемь бизнес-операций.

## 3. Категории

Запрос: `GET /api/categories`. Ответ `200`, порядок `id ASC`:

```json
[
  {"id": 1, "name": "Оборудование"},
  {"id": 2, "name": "Программное обеспечение"},
  {"id": 3, "name": "Доступы"},
  {"id": 4, "name": "Сеть"}
]
```

Идентификаторы иллюстративные. Клиент выбирает ID из полученного справочника. Методов изменения справочника нет.

## 4. Создание и чтение заявки

Запрос: `POST /api/tickets`.

```json
{
  "title": "Не работает принтер",
  "categoryId": 1,
  "description": "Принтер не отвечает.",
  "priority": "HIGH",
  "dueAt": "2026-11-12T15:00:00Z"
}
```

| Поле | Обязательность | Правило |
|---|---|---|
| `title` | Обязательно, не `null` | Исходная строка не длиннее 200 символов, после удаления пробелов по краям непустая; сохраняется очищенное значение |
| `categoryId` | Обязательно, не `null` | Положительный ID существующей категории |
| `description` | Необязательно | До 10 000 символов; пропуск или `null` дают пустую строку |
| `priority` | Необязательно | Пропуск или `null` дают `MEDIUM`; пустая строка и неизвестное значение запрещены |
| `dueAt` | Необязательно | Пропуск или `null` означают отсутствие срока; срок в прошлом допустим |

Ограничения длины строк считаются в кодовых точках Unicode, а не в байтах. Проверка заголовка учитывает строку из пробельных символов, включая табуляции, переводы строк и Unicode-разделители, в том числе неразрывные пробелы. Внутренние пробелы сохраняются. NUL и одиночные UTF-16-суррогаты запрещены; корректные суррогатные пары допустимы. При создании нельзя задать `id`, `status`, `createdAt`, `closedAt` или `overdue`.

Ответ `201` содержит заголовок `Location: /api/tickets/123e4567-e89b-42d3-a456-426614174000` и тело `Ticket`:

```json
{
  "id": "123e4567-e89b-42d3-a456-426614174000",
  "title": "Не работает принтер",
  "description": "Принтер не отвечает.",
  "category": {"id": 1, "name": "Оборудование"},
  "priority": "HIGH",
  "status": "NEW",
  "createdAt": "2026-11-11T09:00:00Z",
  "dueAt": "2026-11-12T15:00:00Z",
  "closedAt": null,
  "overdue": false
}
```

Для `GET /api/tickets/123e4567-e89b-42d3-a456-426614174000` ответ имеет ту же структуру с текущими значениями и кодом `200`. Поле `category` содержит ID и название. `overdue` вычисляется при чтении и не хранится в таблице. В примере контрольное время раньше срока.

Новая заявка всегда имеет `NEW`, `closedAt=null` и пустую историю. Ошибка категории или тела запроса возвращает `400` без создания строки. Отсутствующая заявка при чтении даёт `404`. Повтор POST без механизма идемпотентности создаёт новую заявку; автоматически повторять такой запрос после неопределённого сетевого результата нельзя считать безопасной дедупликацией.

## 5. Замена редактируемых полей

Запрос: `PUT /api/tickets/123e4567-e89b-42d3-a456-426614174000/details`.

```json
{
  "description": "Проверены питание и кабель.",
  "priority": "MEDIUM",
  "dueAt": null
}
```

Это полная замена подресурса редактируемых данных. Все три поля обязательны. Пропуск любого поля даёт `400`. Для очистки описания передаётся `""`, для снятия срока передаётся `null`. Описание и приоритет не принимают `null`. Чтобы изменить только одно значение, клиент передаёт остальные текущие значения вместе с ним.

Ответ `200` имеет структуру `Ticket` из раздела 4: описание и приоритет соответствуют запросу, `dueAt=null`, `overdue=false`. Остальные поля и история не изменяются. Полный пример ответа есть в OpenAPI для `replaceTicketDetails`.

Операция разрешена только для `NEW` и `IN_PROGRESS`. Терминальное состояние даёт `409`, неизвестная заявка даёт `404`, ошибка любого поля даёт `400` без частичного сохранения. Повтор идентичного PUT к открытой заявке допустим и не добавляет историю. При конкурирующих редактированиях более поздняя допустимая операция заменяет набор редактируемых значений; контракт не использует ETag.

## 6. Смена статуса

Запрос: `PATCH /api/tickets/123e4567-e89b-42d3-a456-426614174000/status`.

```json
{"status": "IN_PROGRESS"}
```

Тело содержит только обязательный `status`. Для завершения передаётся `RESOLVED`, для отмены `CANCELLED`. Применяется полная матрица из [процесса обработки](ticket-workflow.md). Ответ `200` имеет структуру `Ticket` с новым состоянием. Время закрытия заполняется при `RESOLVED` и `CANCELLED`, при `IN_PROGRESS` остаётся `null`.

Каждый допустимый переход добавляет ровно одну запись истории в общей транзакции с изменением заявки. Самопереход, возврат назад, пропуск этапа и повторное открытие дают `409` без изменения данных. `NEW` распознаётся как значение статуса, но переход в него не разрешён ни из одного существующего состояния. Неизвестное имя статуса даёт `400`.

## 7. История

Запрос: `GET /api/tickets/123e4567-e89b-42d3-a456-426614174000/history`. Ответ `200` после перевода в работу:

```json
[
  {
    "id": 1,
    "fromStatus": "NEW",
    "toStatus": "IN_PROGRESS",
    "changedAt": "2026-11-11T09:30:00Z"
  }
]
```

Порядок `id ASC`. У новой заявки возвращается `[]`, у отсутствующей заявки `404`. Создание не записывается как переход. Для терминального перехода `changedAt` равно `closedAt`. Чтение не изменяет данные.

## 8. Поиск и пагинация

Пример запроса: `GET /api/tickets?status=NEW&priority=HIGH&categoryId=1&overdue=false&page=0&size=20`.

| Параметр | Значение по умолчанию | Ограничение |
|---|---|---|
| `status` | Фильтр отсутствует | Одно значение enum |
| `priority` | Фильтр отсутствует | Одно значение enum |
| `categoryId` | Фильтр отсутствует | Положительный `int64`; неизвестный ID даёт пустой результат |
| `overdue` | Фильтр отсутствует | Только `true` или `false` |
| `page` | `0` | Целое от 0 до 2 147 483 647 |
| `size` | `20` | Целое от 1 до 100 |

Числовые query-параметры передаются десятичными цифрами `0-9`, без знака, пробелов, дробной части и экспоненты. Значения enum регистрозависимы. Пустое значение, повтор параметра и неизвестное имя дают `400`. Все фильтры соединяются через AND. Порядок фиксирован: `createdAt DESC, id DESC`; пользовательский параметр сортировки не поддерживается. `overdue=true` выбирает только открытые заявки с непустым сроком строго раньше контрольного времени. `overdue=false` выбирает все остальные, включая заявки без срока и терминальные заявки.

Ответ `200` имеет поля `content` (массив `Ticket`), `page`, `size`, `totalElements`, `totalPages`. `totalPages = ceil(totalElements / size)`. При отсутствии совпадений:

```json
{"content": [], "page": 0, "size": 20, "totalElements": 0, "totalPages": 0}
```

Страница за концом непустого результата также пуста, но общее количество и число страниц остаются фактическими. Стабильность страниц гарантируется для неизменных данных, а не между запросами на фоне конкурентных изменений. Полный непустой пример находится в OpenAPI для `listTickets`.

## 9. Статистика

Пример запроса: `GET /api/reports/summary?from=2026-11-01T00:00:00Z&to=2026-11-12T00:00:00Z`.

Обе границы обязательны, `from < to`. В выборку входят только заявки с `from <= createdAt < to`. Все показатели рассчитываются Kotlin-сервисом по одной выборке; используются текущие состояния и один контрольный момент просрочки.

Ответ `200` для иллюстративного набора из четырёх заявок:

```json
{
  "from": "2026-11-01T00:00:00Z",
  "to": "2026-11-12T00:00:00Z",
  "totalCreated": 4,
  "byStatus": {"NEW": 1, "IN_PROGRESS": 1, "RESOLVED": 2, "CANCELLED": 0},
  "byPriority": {"LOW": 1, "MEDIUM": 1, "HIGH": 2},
  "openOverdue": 1,
  "averageResolutionSeconds": 7200
}
```

Все группы присутствуют, включая нулевые. Обе суммы распределений равны `totalCreated`. Счётчики неотрицательны. Среднее считается только по `RESOLVED`, в секундах между созданием и закрытием, с округлением до шести знаков `HALF_UP` после деления суммы на количество. Время закрытия может быть вне периода. Например, длительности 3600 и 10800 секунд дают среднее 7200.

Для пустой выборки ответ:

```json
{
  "from": "2026-11-01T00:00:00Z",
  "to": "2026-11-12T00:00:00Z",
  "totalCreated": 0,
  "byStatus": {"NEW": 0, "IN_PROGRESS": 0, "RESOLVED": 0, "CANCELLED": 0},
  "byPriority": {"LOW": 0, "MEDIUM": 0, "HIGH": 0},
  "openOverdue": 0,
  "averageResolutionSeconds": null
}
```

Среднее также равно `null` при непустой выборке без `RESOLVED`. Неверный период даёт `400`; неподходящих заявок недостаточно для ошибки `404`, вместо неё возвращается пустая статистика.

## 10. Единый формат ошибок

| HTTP | `code` | Причина |
|---|---|---|
| `400` | `INVALID_REQUEST` | Повреждённый JSON, неверный тип, формат UUID или даты, enum, неизвестный параметр или поле |
| `400` | `VALIDATION_ERROR` | Отсутствующее обязательное поле, нарушение длины, неизвестная категория при создании, недопустимый период или границы пагинации |
| `404` | `TICKET_NOT_FOUND` | Заявка с корректным UUID отсутствует |
| `409` | `STATE_CONFLICT` | Запрещённый переход или редактирование терминальной заявки |
| `405` | `METHOD_NOT_ALLOWED` | Неподдерживаемый HTTP-метод для существующего маршрута |
| `406` | `NOT_ACCEPTABLE` | Несовместимый формат ответа в Accept |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Тело передано не как JSON |
| `500` | `INTERNAL_ERROR` | Неожиданная ошибка выполнения или сохранения |

Пример отклонения запрещённого перехода:

```json
{
  "timestamp": "2026-11-11T10:00:00Z",
  "status": 409,
  "code": "STATE_CONFLICT",
  "message": "Операция запрещена для текущего состояния заявки.",
  "path": "/api/tickets/123e4567-e89b-42d3-a456-426614174000/status",
  "violations": []
}
```

`timestamp` берётся из `Clock`, `status` совпадает с HTTP-кодом, `path` содержит фактический путь запроса без query. `violations` всегда массив объектов `{field, message}`. Для ошибки поля указывается его имя, для неверного порядка периода указывается `period`; при ошибке без конкретного поля массив пуст. Сообщения на русском; клиент ориентируется на HTTP-код и `code`, точный текст сообщения не является стабильным идентификатором ошибки.

Ответ ошибки использует JSON, в том числе при несовместимом Accept. В ответ не попадают SQL, трассировка стека, пароли или текст внутренних исключений. При запрете операции поля заявки и все записи истории остаются прежними. При искусственно вызванном сбое записи истории ожидаются `500` и полный откат. Ошибки неверного URL вне перечисленных маршрутов и ответы внешнего прокси не описываются этим контрактом бизнес-API.

## 11. Проверка и последующая актуализация

До реализации проверяются структура OpenAPI, локальные ссылки, соответствие примеров схемам и согласованность документов. Семантические правила проверяются по данным и сценариям тест-плана. Это не считается успешным выполнением будущих HTTP-тестов.

После реализации OpenAPI работающего приложения сверяется с этим файлом по маршрутам, схемам и статусам. Контракт, примеры и автотесты обновляются вместе. На BL-20 добавляется проверенная коллекция запросов и демонстрационные данные.
