## Правила планирования

- **P0** - задача, от которой зависит обязательное условие зачёта, целостность данных или возможность выполнения следующих этапов.
- **P1** - обязательная задача для полноты функциональности, подтверждения качества или сдачи материалов; выполняется с учётом зависимостей после необходимых P0.
- Все задачи входят в согласованный объём. Приоритет P1 не означает, что задачу можно исключить.
- **Завершено** - результат подготовлен, проверен и зафиксирован коммитом; для исполняемого результата требуется соответствующая проверка работы.
- **Подготовлено** - результат подготовлен и проверен, но ещё не зафиксирован коммитом.
- **Запланировано** - выполнение ещё не начато.
- Одна строка соответствует планируемому тематическому коммиту. Исправления реальных дефектов могут потребовать нескольких коммитов внутри оценки BL-18.
- Тесты и документация сопровождают функциональные изменения. Отдельные задачи тестирования дополняют проверки, а не откладывают написание всех тестов до конца реализации.
- Поле «Зависит от» перечисляет непосредственные зависимости; зависимости этих задач учитываются транзитивно. Номера задают рекомендуемый порядок выполнения.

## Внешние зависимости и риски

- До BL-24 нужны удалённый репозиторий, доступ к pull request и запуску GitHub Actions; до BL-25 - registry и разрешение публикации; до BL-26 - стенд и runner. Их доступность проверяется при подготовке проекта, чтобы не откладывать организационные вопросы до доставки.
- До интеграционных тестов и контейнеризации нужен работающий Docker с возможностью запуска PostgreSQL. Доступность проверяется при настройке окружения в BL-05.
- Для отката требуются две доступные версии образа и обратно совместимые миграции. Первая успешная версия сохраняется при BL-26; проверка BL-27 выполняется после доставки следующей проверенной версии, без перезаписи исходного SHA-тега.
- BL-18 является резервом на фактически найденные дефекты. Ошибки можно исправлять раньше при обнаружении; описание и регрессия сохраняются. Намеренное внесение ошибки не заменяет поиск дефекта, а отсутствие находок не является основанием объявлять требование выполненным.
- Реальные пароли и токены передаются средствами окружения и секретов CI/CD; в документы включаются только имена параметров и примеры без реальных значений.

## Порядок работы с Git

Первый коммит содержит исходные требования. Этапы историй, архитектуры, контракта, сборки и миграций выполнены в `docs/user-stories-backlog`, `docs/architecture-data-model`, `docs/api-contract-test-plan`, `build/java-kotlin-bootstrap` и `feature-c/postgresql-migrations`. API создания и чтения зафиксировано в `feature-c/ticket-create-read-api`. Валидация зафиксирована в `feature-c/request-validation`. Редактирование зафиксировано в `feature-c/ticket-details`. Переходы и история зафиксированы в `feature-c/ticket-status-history`. Поиск зафиксирован в `feature-c/ticket-search`. Расчёт отчёта зафиксирован в `feature-c/report-calculation`. HTTP-отчёт зафиксирован в `feature-c/report-api`. Границы отчёта зафиксированы в `feature-c/report-boundaries`. Модульные проверки зафиксированы в `feature-c/unit-business-rules`. Интеграционные проверки зафиксированы в `feature-c/integration-contract`. Сквозные сценарии зафиксированы в `feature-c/end-to-end-scenarios`. Проверка регрессий зафиксирована в `feature-c/defect-regression`. Покрытие зафиксировано в `feature-c/test-coverage`. Материалы API зафиксированы в `feature-c/api-demo-materials`. Контейнеризация зафиксирована в `feature-c/docker-compose`. Текущий этап подготавливается в `feature-c/database-backup` от коммита `2f919dd`. Ветки продолжают общую историю; выше указаны идентификаторы текущей истории Git. После появления удалённого репозитория изменения объединяются через pull request; локальная ветка сама по себе не считается выполненным pull request.

Перед каждым коммитом проверяются изменённые файлы, связанные критерии и актуальность README. Результат этапа фиксируется отдельным сообщением коммита на английском языке. Коммит выполняется после отдельной проверки подготовленных изменений.
