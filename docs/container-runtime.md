# Контейнерный запуск и сохранность данных

**Автор:** Васильев Юрий, 4П1.23

## 1. Состав

Dockerfile содержит два этапа:

1. build: Eclipse Temurin JDK 25, Gradle Wrapper и исходники. Команда bootJar собирает приложение с Java/Kotlin, миграциями и OpenAPI.
2. runtime: Eclipse Temurin JRE 25, curl для HTTP health check и один исполняемый JAR. Пользователь support имеет UID/GID 10001; Gradle и исходники приложения в финальный образ не копируются.

Базовые JDK/JRE закреплены digest OCI index в Dockerfile; PostgreSQL 18.6 закреплён digest в compose.yaml. На проверенном linux/amd64 используется Temurin 25.0.5+8. Обновление образов выполняется явным изменением digest и повторной проверкой. curl устанавливается из репозитория Ubuntu во время сборки; версия системного пакета отдельно не закреплена, поэтому побайтовая идентичность образов между разными датами сборки не заявляется. Версии Java/Kotlin-зависимостей и Wrapper закреплены независимо.

BuildKit кеширует Gradle в отдельном cache mount; кеш ускоряет повторную сборку и не входит в образ. `.dockerignore` разрешает только сборочные файлы, Wrapper, src/main и docs/openapi.yaml. Git, локальный build, тесты, `.env`, резервные копии и остальные документы не передаются в контекст.

Docker-сборка не запускает Testcontainers: bootJar не зависит от test. Перед публикацией образа необходим успешный `gradlew.bat build`; проверка в pipeline будет добавлена на BL-24. Docker socket внутрь сборки и приложения не передаётся.

## 2. Compose и переменные

Compose содержит сервисы postgres и app, отдельную сеть проекта и том postgres-data. Приложение ожидает healthy базы через depends_on, затем Flyway применяет миграции и Hibernate проверяет схему. Проверка приложения наследуется из Dockerfile и вызывает `/actuator/health/readiness`; группа включает состояние readiness и подключение к БД. `pg_isready` проверяет готовность сервера PostgreSQL, но сам по себе не проверяет пароль приложения.

Порядок запуска описан в [документации Compose](https://docs.docker.com/compose/how-tos/startup-order/). Для [официального PostgreSQL 18](https://hub.docker.com/_/postgres) том смонтирован в `/var/lib/postgresql`, данные находятся в подкаталоге версии. Старый путь `/var/lib/postgresql/data` не используется.

| Переменная .env | Значение шаблона | Назначение |
|---|---|---|
| DB_NAME | support_service | Имя базы внутри PostgreSQL |
| DB_USERNAME | support_service | Пользователь для инициализации базы и подключения приложения |
| DB_PASSWORD | Пусто | Обязательный локальный пароль, задаётся до запуска |
| APP_PORT | 8080 | Порт компьютера, публикация только на 127.0.0.1 |
| APP_IMAGE | support-service:local | Имя и тег локально собираемого образа |

В контейнере app SERVER_PORT всегда 8080, DB_URL формируется как jdbc:postgresql://postgres:5432/DB_NAME. Переменная DB_URL локального JAR не используется для выбора базы Compose. Порт PostgreSQL на компьютер не публикуется. `.env` обрабатывает Compose, а не Spring Boot; приложение получает уже сформированные переменные окружения.

Compose отказывается обрабатывать конфигурацию при пустом DB_PASSWORD. Для первичной настройки скопировать `.env.example` в `.env`, заполнить пароль и при необходимости APP_PORT. При существующем `.env` не заменять его шаблоном. Значения переменных текущего shell имеют приоритет над `.env`; перед проверкой нового окружения учитывать ранее заданные DB_USERNAME/DB_PASSWORD.

POSTGRES_DB/USER/PASSWORD применяются официальным образом при создании пустого тома. Изменение `.env` не меняет пароль и пользователя уже существующей базы: для этого требуется явное управление PostgreSQL. Не удалять том ради смены пароля.

## 3. Запуск и остановка

Предварительные условия: Docker Engine с Linux-контейнерами, Docker Compose v2, доступ к Docker Hub, репозиториям Ubuntu, Gradle и Maven при первой сборке. Локальные JDK/Gradle не нужны для Compose. Команды выполняются из корня проекта:

```powershell
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 180
docker compose ps
Invoke-RestMethod 'http://localhost:8080/actuator/health/readiness'
Invoke-RestMethod 'http://localhost:8080/api/categories'
```

Ожидаются healthy для обоих сервисов, HTTP 200 и status UP, четыре категории. При другом APP_PORT заменить порт URL. Swagger UI и коллекция описаны в [демонстрации API](api-demo.md). Коллекцию можно запускать на новой пустой базе Compose, но она останавливается, если заявки уже есть.

```powershell
docker compose logs --tail 100 app postgres
docker compose logs -f app
docker compose stop
docker compose up -d --wait --wait-timeout 180
```

Логи пишутся в stdout/stderr. Ctrl+C после logs -f останавливает просмотр, а не контейнеры. Полная остановка с удалением контейнеров и сети:

```powershell
docker compose down
docker compose up -d --wait --wait-timeout 180
```

Том postgres-data сохраняется. Compose добавляет к имени тома имя проекта, по умолчанию support-service. Использовать одинаковое имя проекта при последующих запусках. Параметр `-p другое-имя` создаёт другое окружение с собственным томом; пустой список заявок в нём не означает потерю исходных данных.

Команда down -v удаляет том с данными и не входит в обычную остановку. Для независимой учебной проверки использовать отдельное имя проекта и свободный APP_PORT. Контейнеры используют restart unless-stopped; статус unhealthy сам по себе не перезапускает работающий процесс. Разбор отказов и восстановления выделен в BL-23.

## 4. Проверка сохранности

После создания заявки и переходов через API сохранить её JSON и весь массив истории. Выполнить down без -v, затем up с тем же именем проекта и окружением. Прочитать ту же заявку и историю и сравнить значения. Для терминальной заявки поле overdue стабильно; у открытой заявки с близким сроком оно может измениться из-за текущего времени даже при неизменной БД.

Дополнительно проверить в PostgreSQL таблицы categories, tickets, ticket_status_history и flyway_schema_history. Миграции V1 и V2 должны оставаться единственными успешно применёнными версиями. Простой ответ health UP не доказывает сохранность данных.
